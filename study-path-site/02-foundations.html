Performance vs. scalability

A service is scalable if it achieves increased performance in a manner proportional to resources added. Increasing performance usually means serving more units of work, though it can also mean handling larger units of work as datasets grow.

The simplest way to tell the two apart:

  • If you have a performance problem, your system is slow for a single user.
  • If you have a scalability problem, your system is fast for a single user but slow under heavy load.

Why this distinction matters later: a lot of "scaling" techniques you'll meet in Modules 05–09 (load balancers, caching, sharding) do nothing for a single slow request — they only help when many requests arrive at once. Keep asking yourself, for every technique: is this fixing speed, or fixing capacity under load?

Source: A word on scalability, Scalability, availability, stability, patterns

Latency vs. throughput

Latency is the time to perform some action or produce some result. Throughput is the number of such actions or results per unit of time.

Generally, you should aim for maximal throughput with acceptable latency — not minimal latency at any cost, and not maximal throughput regardless of how slow any single request feels.

Handy metrics derived from the numbers above:

  • Read sequentially from HDD at ~30 MB/s
  • Read sequentially from 1 Gbps Ethernet at ~100 MB/s
  • Read sequentially from SSD at ~1 GB/s
  • Read sequentially from main memory at ~4 GB/s
  • 6–7 world-wide round trips per second
  • 2,000 round trips per second within a data center
