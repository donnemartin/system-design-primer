MODULE 14 · SYSTEM DESIGN SOLUTION

Solution to the exercise: "Design the data structures for a social network"

Social Graph

The whole exercise, deliberately: find the shortest chain of friends between two people — "degrees of separation" — without reaching for a purpose-built graph database. The constraint is the point: it forces you to think about sharding a graph across machines.

Framework step 1 · Module 01Use cases & constraints

  • User searches for someone and sees the shortest path connecting them
  • Service is highly available
Deliberately out of reach: graph-native tools like Neo4j or GraphQL — this is solved with plain services and sharding instead.
  • 100 million users, ~50 friends each on average → 5 billion friend-relationship edges; graph edges are unweighted
  • The whole graph won't fit on one machine
  • 1 billion friend searches/month → ~400 search requests/sec on average

Framework step 2 · Module 01High-level design

If the graph fit in memory on one machine, this would just be unweighted shortest-path BFS:

Plain BFS shortest path (no sharding constraint)
class Graph(Graph):

    def shortest_path(self, source, dest):
        if source is None or dest is None:
            return None
        if source is dest:
            return [source.key]
        prev_node_keys = self._shortest_path(source, dest)
        if prev_node_keys is None:
            return None
        else:
            path_ids = [dest.key]
            prev_node_key = prev_node_keys[dest.key]
            while prev_node_key is not None:
                path_ids.append(prev_node_key)
                prev_node_key = prev_node_keys[prev_node_key]
            return path_ids[::-1]

    def _shortest_path(self, source, dest):
        queue = deque()
        queue.append(source)
        prev_node_keys = {source.key: None}
        source.visit_state = State.visited
        while queue:
            node = queue.popleft()
            if node is dest:
                return prev_node_keys
            prev_node = node
            for adj_node in node.adj_nodes.values():
                if adj_node.visit_state == State.unvisited:
                    queue.append(adj_node)
                    prev_node_keys[adj_node.key] = prev_node.key
                    adj_node.visit_state = State.visited
        return None

But 100 million users won't fit on one machine. So users (vertices) get sharded across many Person Servers, and a Lookup Service maps a person id to the server that holds them.

Framework step 3 · Module 01Core components

  1. Client → Web Server (reverse proxy) → Search API → User Graph Service
  2. User Graph Service asks the Lookup Service which Person Server holds the current user, fetches their friend_ids
  3. Runs BFS with the current user as source — but every time it needs a friend's data (an adjacent node), it has to ask the Lookup Service again for that friend's Person Server. That extra round-trip per hop is exactly the scaling pain point this design has to manage.

class UserGraphService(object):

    def __init__(self, lookup_service):
        self.lookup_service = lookup_service

    def person(self, person_id):
        person_server = self.lookup_service.lookup_person_server(person_id)
        return person_server.people([person_id])

    def shortest_path(self, source_key, dest_key):
        if source_key is None or dest_key is None:
            return None
        if source_key is dest_key:
            return [source_key]
        prev_node_keys = self._shortest_path(source_key, dest_key)
        if prev_node_keys is None:
            return None
        else:
            path_ids = [dest_key]
            prev_node_key = prev_node_keys[dest_key]
            while prev_node_key is not None:
                path_ids.append(prev_node_key)
                prev_node_key = prev_node_keys[prev_node_key]
            return path_ids[::-1]

    def _shortest_path(self, source_key, dest_key, path):
        source = self.person(source_key)
        queue = deque()
        queue.append(source)
        prev_node_keys = {source_key: None}
        visited_ids = set()
        visited_ids.add(source.id)
        while queue:
            node = queue.popleft()
            if node.key is dest_key:
                return prev_node_keys
            prev_node = node
            for friend_id in node.friend_ids:
                if friend_id not in visited_ids:
                    friend_node = self.person(friend_id)
                    queue.append(friend_node)
                    prev_node_keys[friend_id] = prev_node.key
                    visited_ids.add(friend_id)
        return None

Framework step 4 · Module 01Scaling the design

Benchmark → profile → fix the real bottleneck → repeat. See Scaling to millions on AWS for a worked example.

The ~400 average search requests/sec push toward a Memory Cache in front of person data — especially valuable for well-connected users and for anyone doing repeated searches (memory reads run ~250μs vs. 4x on SSD, 80x on disk).

The graph-specific optimizations are the interesting part of this one:

  • Cache complete or partial BFS traversals so a repeated or similar search doesn't redo the walk
  • Batch-compute common traversals offline and store them in a NoSQL store for fast lookup
  • Batch friend lookups that happen to live on the same Person Server to cut down on machine hops — and shard Person Servers by geography, since friends tend to live near each other, which increases the odds a batch stays on one server
  • Run BFS from both ends at once — source→dest and dest→source — and meet in the middle, which is dramatically faster than a one-directional search on a graph this size
  • Start from highly-connected people first, since they're statistically more likely to shortcut the "six degrees of separation" path
  • Cap the search by time or hop count and ask the user if they want to keep going, since worst-case BFS here can take a while
  • And, if the constraint were lifted: a real graph database (Neo4j) or GraphQL would do a lot of this natively
