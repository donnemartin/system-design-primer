## પ્રેરણા

> મોટા પાયે સિસ્ટમ કેવી રીતે ડિઝાઇન કરવી તે જાણો.
>
> સિસ્ટમ ડિઝાઇન ઇન્ટરવ્યુ માટે તૈયારી.

### મોટા પાયે સિસ્ટમ કેવી રીતે ડિઝાઇન કરવી તે જાણો

સ્કેલેબલ સિસ્ટમ્સ કેવી રીતે ડિઝાઇન કરવી તે શીખવું તમને વધુ સારા એન્જિનિયર બનવામાં મદદ કરશે.

સિસ્ટમ ડિઝાઇન એ એક વ્યાપક વિષય છે.  સિસ્ટમ ડિઝાઇન સિદ્ધાંતો પર **વેબ પર પથરાયેલાં સંસાધનોની વિશાળ સંખ્યા** છે.

આ રેપો એ સંસાધનોનો **સંગઠિત સંગ્રહ** છે જે તમને સ્કેલ પર સિસ્ટમ્સ કેવી રીતે બનાવવી તે શીખવામાં મદદ કરે છે.

### ઓપન સોર્સ સમુદાયમાંથી શીખો

આ એક સતત અપડેટ થતો, ઓપન સોર્સ પ્રોજેક્ટ છે.

[યોગદાન](# યોગદાન) આવકાર્ય છે!

### સિસ્ટમ ડિઝાઇન ઇન્ટરવ્યુ માટે તૈયારી

ઇન્ટરવ્યુ કોડિંગ ઉપરાંત, સિસ્ટમ ડિઝાઇન એ ઘણી ટેક કંપનીઓમાં **તકનીકી ઇન્ટરવ્યુ પ્રક્રિયા**નો **જરૂરી ઘટક** છે.

**સામાન્ય સિસ્ટમ ડિઝાઇન ઇન્ટરવ્યુ પ્રશ્નોની પ્રેક્ટિસ કરો** અને તમારા પરિણામોની **સેમ્પલ સોલ્યુશન્સ** સાથે **સરખાવો**: ચર્ચાઓ, કોડ અને આકૃતિઓ.

ઇન્ટરવ્યૂની તૈયારી માટે વધારાના વિષયો:

* [અભ્યાસ માર્ગદર્શિકા](#સ્ટડી-માર્ગદર્શિકા)
* [સિસ્ટમ ડિઝાઇન ઇન્ટરવ્યુ પ્રશ્નનો સંપર્ક કેવી રીતે કરવો]
* [સિસ્ટમ ડિઝાઇન ઇન્ટરવ્યુ પ્રશ્નો, **સોલ્યુશન્સ સાથે**](#સિસ્ટમ-ડિઝાઇન-ઇન્ટરવ્યુ-પ્રશ્નો-સોલ્યુશન્સ સાથે)
* [ઑબ્જેક્ટ-ઓરિએન્ટેડ ડિઝાઇન ઇન્ટરવ્યુ પ્રશ્નો, **સોલ્યુશન્સ સાથે**](#ઑબ્જેક્ટ-ઓરિએન્ટેડ-ડિઝાઇન-ઇન્ટરવ્યુ-પ્રશ્નો-સાધનો)
* [અતિરિક્ત સિસ્ટમ ડિઝાઇન ઇન્ટરવ્યુ પ્રશ્નો](#વધારાની-સિસ્ટમ-ડિઝાઇન-ઇન્ટરવ્યૂ-પ્રશ્નો)

## અભ્યાસ માર્ગદર્શિકા

> તમારી ઇન્ટરવ્યુની સમયરેખા (ટૂંકા, મધ્યમ, લાંબી)ના આધારે સમીક્ષા કરવા માટે સૂચવેલા વિષયો.

![Imgur](images/OfVllex.png)

**પ્ર: ઇન્ટરવ્યુ માટે, શું મારે અહીં બધું જાણવાની જરૂર છે?**

**A: ના, ઇન્ટરવ્યૂની તૈયારી કરવા માટે તમારે અહીં બધું જાણવાની જરૂર નથી**.

ઇન્ટરવ્યુમાં તમને જે પૂછવામાં આવે છે તે ચલો પર આધારિત છે જેમ કે:

* તમારી પાસે કેટલો અનુભવ છે
* તમારી તકનીકી પૃષ્ઠભૂમિ શું છે
* તમે કયા હોદ્દા માટે ઇન્ટરવ્યુ લઈ રહ્યા છો
* તમે કઈ કંપનીઓ સાથે ઈન્ટરવ્યુ લઈ રહ્યા છો
* નસીબ

વધુ અનુભવી ઉમેદવારો સામાન્ય રીતે સિસ્ટમ ડિઝાઇન વિશે વધુ જાણવાની અપેક્ષા રાખે છે.  આર્કિટેક્ટ અથવા ટીમ લીડ્સ વ્યક્તિગત યોગદાનકર્તાઓ કરતાં વધુ જાણવાની અપેક્ષા રાખી શકાય છે.  ટોચની ટેક કંપનીઓમાં એક અથવા વધુ ડિઝાઇન ઇન્ટરવ્યુ રાઉન્ડ હોય તેવી શક્યતા છે.

વ્યાપક પ્રારંભ કરો અને થોડા વિસ્તારોમાં ઊંડા જાઓ.  તે વિવિધ કી સિસ્ટમ ડિઝાઇન વિષયો વિશે થોડું જાણવામાં મદદ કરે છે.  તમારી સમયરેખા, અનુભવ, તમે કઈ હોદ્દા માટે ઈન્ટરવ્યુ લઈ રહ્યા છો અને કઈ કંપનીઓ સાથે ઈન્ટરવ્યુ લઈ રહ્યા છો તેના આધારે નીચેની માર્ગદર્શિકાને સમાયોજિત કરો.

* **ટૂંકી સમયરેખા** - સિસ્ટમ ડિઝાઇન વિષયો સાથે **વિસ્તૃત** માટે લક્ષ્ય રાખો.  **કેટલાક** ઇન્ટરવ્યુ પ્રશ્નો હલ કરીને પ્રેક્ટિસ કરો.
* **મધ્યમ સમયરેખા** - સિસ્ટમ ડિઝાઇન વિષયો સાથે **પહોળાઈ** અને **કેટલીક ઊંડાઈ** માટે લક્ષ્ય રાખો.  **ઘણા** ઇન્ટરવ્યુ પ્રશ્નો હલ કરીને પ્રેક્ટિસ કરો.
* **લાંબી સમયરેખા** - સિસ્ટમ ડિઝાઇન વિષયો સાથે **પહોળાઈ** અને **વધુ ઊંડાણ** માટે લક્ષ્ય રાખો.  **મોટા ભાગના** ઇન્ટરવ્યુ પ્રશ્નો હલ કરીને પ્રેક્ટિસ કરો.

## સિસ્ટમ ડિઝાઇન ઇન્ટરવ્યુ પ્રશ્નનો સંપર્ક કેવી રીતે કરવો

> સિસ્ટમ ડિઝાઇન ઇન્ટરવ્યુ પ્રશ્નનો સામનો કેવી રીતે કરવો.

સિસ્ટમ ડિઝાઇન ઇન્ટરવ્યુ એ **ખુલ્લી વાતચીત** છે.  તમે તેનું નેતૃત્વ કરશો તેવી અપેક્ષા છે.

તમે ચર્ચાને માર્ગદર્શન આપવા માટે નીચેના પગલાંનો ઉપયોગ કરી શકો છો.  આ પ્રક્રિયાને મજબૂત બનાવવામાં મદદ કરવા માટે, નીચેના પગલાંઓનો ઉપયોગ કરીને [સિસ્ટમ ડિઝાઇન ઇન્ટરવ્યુ પ્રશ્નોના ઉકેલો](#system-design-interview-questions-with-solutions) વિભાગ દ્વારા કામ કરો.

### પગલું 1: ઉપયોગના કિસ્સાઓ, અવરોધો અને ધારણાઓની રૂપરેખા

જરૂરિયાતો એકત્રિત કરો અને સમસ્યાનો વિસ્તાર કરો.  ઉપયોગના કિસ્સાઓ અને અવરોધોને સ્પષ્ટ કરવા માટે પ્રશ્નો પૂછો.  ધારણાઓની ચર્ચા કરો.

* તેનો ઉપયોગ કોણ કરશે?
* તેઓ તેનો ઉપયોગ કેવી રીતે કરશે?
* ત્યાં કેટલા વપરાશકર્તાઓ છે?
* સિસ્ટમ શું કરે છે?
* સિસ્ટમના ઇનપુટ અને આઉટપુટ શું છે?
* આપણે કેટલો ડેટા હેન્ડલ કરવાની અપેક્ષા રાખીએ છીએ?
* અમે પ્રતિ સેકન્ડમાં કેટલી વિનંતીઓની અપેક્ષા રાખીએ છીએ?
* અપેક્ષિત રીડ ટુ રાઈટ રેશિયો શું છે?

### પગલું 2: ઉચ્ચ સ્તરની ડિઝાઇન બનાવો

બધા મહત્વપૂર્ણ ઘટકો સાથે ઉચ્ચ સ્તરીય ડિઝાઇનની રૂપરેખા બનાવો.

* મુખ્ય ઘટકો અને જોડાણોને સ્કેચ કરો
* તમારા વિચારોને ન્યાય આપો

### પગલું 3: મુખ્ય ઘટકો ડિઝાઇન કરો

દરેક મુખ્ય ઘટક માટે વિગતોમાં ડાઇવ કરો.  ઉદાહરણ તરીકે, જો તમને [url શોર્ટનિંગ સર્વિસ ડિઝાઇન](solutions/system_design/pastebin/README.md) કરવાનું કહેવામાં આવ્યું હોય, તો ચર્ચા કરો:

* સંપૂર્ણ url નું હેશ જનરેટ અને સ્ટોર કરવું
    * [MD5](solutions/system_design/pastebin/README.md) અને [Base62](solutions/system_design/pastebin/README.md)
    * હેશ અથડામણ
    * SQL અથવા NoSQL
    * ડેટાબેઝ સ્કીમા
* હેશ કરેલ url ને સંપૂર્ણ url માં અનુવાદિત કરવું
    * ડેટાબેઝ લુકઅપ
* API અને ઑબ્જેક્ટ-ઓરિએન્ટેડ ડિઝાઇન

### પગલું 4: ડિઝાઇનને સ્કેલ કરો

અવરોધોને જોતાં, અવરોધોને ઓળખો અને સંબોધિત કરો.  ઉદાહરણ તરીકે, શું તમને માપનીયતાના મુદ્દાઓને સંબોધવા માટે નીચેનાની જરૂર છે?

* લોડ બેલેન્સર
* આડું સ્કેલિંગ
* કેશીંગ
* ડેટાબેઝ શેરિંગ

સંભવિત ઉકેલો અને ટ્રેડ-ઓફની ચર્ચા કરો.  બધું એક વેપાર બંધ છે.  [સ્કેલેબલ સિસ્ટમ ડિઝાઇનના સિદ્ધાંતો](#index-of-system-design-topics) નો ઉપયોગ કરીને અડચણોને દૂર કરો.

## પ્રદર્શન વિ માપનીયતા

A service is **scalable** if it results in increased **performance** in a manner proportional to resources added. Generally, increasing performance means serving more units of work, but it can also be to handle larger units of work, such as when datasets grow.<sup><a href=http://www.allthingsdistributed.com/2006/03/a_word_on_scalability.html>1</a></sup>

પ્રદર્શન વિ માપનીયતાને જોવાની બીજી રીત:

* જો તમને **પ્રદર્શન** સમસ્યા હોય, તો તમારી સિસ્ટમ એકલ વપરાશકર્તા માટે ધીમી છે.
* જો તમને **સ્કેલેબિલિટી** સમસ્યા હોય, તો તમારી સિસ્ટમ એકલ વપરાશકર્તા માટે ઝડપી છે પરંતુ ભારે ભાર હેઠળ ધીમી છે.

## ઉપલબ્ધતા વિ સુસંગતતા

### CAP પ્રમેય

<p align="center">
  <img src="images/bgLMI2u.png">
  <br/>
  <i><a href="https://robertgreiner.com/cap-theorem-revisited">Source: CAP theorem revisited</a></i>
</p>

વિતરિત કોમ્પ્યુટર સિસ્ટમમાં, તમે નીચેની બાંયધરીમાંથી ફક્ત બેને જ સમર્થન આપી શકો છો:

* **સંગતતા** - દરેક વાંચન સૌથી તાજેતરનું લખાણ અથવા ભૂલ પ્રાપ્ત કરે છે
* **ઉપલબ્ધતા** - દરેક વિનંતીને પ્રતિસાદ મળે છે, તે ગેરેંટી વિના કે તેમાં માહિતીનું સૌથી તાજેતરનું સંસ્કરણ છે
* **પાર્ટીશન ટોલરન્સ** - નેટવર્ક નિષ્ફળતાને કારણે મનસ્વી રીતે પાર્ટીશન કરવા છતાં સિસ્ટમ કાર્યરત રહે છે

*નેટવર્ક વિશ્વસનીય નથી, તેથી તમારે પાર્ટીશન સહિષ્ણુતાને સમર્થન આપવું પડશે.  તમારે સુસંગતતા અને ઉપલબ્ધતા વચ્ચે સોફ્ટવેર ટ્રેડઓફ કરવાની જરૂર પડશે.*

#### CP - સુસંગતતા અને પાર્ટીશન સહિષ્ણુતા

પાર્ટીશન કરેલ નોડમાંથી પ્રતિસાદની રાહ જોવાથી સમય સમાપ્તિ ભૂલ થઈ શકે છે.  જો તમારા વ્યવસાયને એટોમિક રીડ અને રાઇટની જરૂર હોય તો CP એ સારી પસંદગી છે.

#### એપી - ઉપલબ્ધતા અને પાર્ટીશન સહિષ્ણુતા

પ્રતિભાવો કોઈપણ નોડ પર ઉપલબ્ધ ડેટાનું સૌથી સહેલાઈથી ઉપલબ્ધ સંસ્કરણ પરત કરે છે, જે કદાચ નવીનતમ ન હોય.  જ્યારે પાર્ટીશન ઉકેલાઈ જાય ત્યારે રાઈટ્સને પ્રચારમાં થોડો સમય લાગી શકે છે.

AP એ સારી પસંદગી છે જો વ્યવસાયને [અંતિમ સુસંગતતા](#eventual-consistency) માટે પરવાનગી આપવાની જરૂર હોય અથવા જ્યારે સિસ્ટમને બાહ્ય ભૂલો હોવા છતાં કામ કરવાનું ચાલુ રાખવાની જરૂર હોય.

## સુસંગતતા પેટર્ન

સમાન ડેટાની બહુવિધ નકલો સાથે, અમે તેમને કેવી રીતે સમન્વયિત કરવું તે અંગેના વિકલ્પોનો સામનો કરી રહ્યા છીએ જેથી ક્લાયંટ ડેટાને સતત જોઈ શકે.  [CAP પ્રમેય](#cap-theorem) માંથી સુસંગતતાની વ્યાખ્યા યાદ કરો - દરેક વાંચન સૌથી તાજેતરનું લખાણ અથવા ભૂલ પ્રાપ્ત કરે છે.

### નબળી સુસંગતતા

લખ્યા પછી, વાંચે છે કે ન પણ જોઈ શકે.  શ્રેષ્ઠ પ્રયાસનો અભિગમ અપનાવવામાં આવે છે.

આ અભિગમ memcached જેવી સિસ્ટમોમાં જોવા મળે છે.  નબળા સુસંગતતા વાસ્તવિક સમયના ઉપયોગના કેસોમાં સારી રીતે કામ કરે છે જેમ કે VoIP, વિડિઓ ચેટ અને રીઅલટાઇમ મલ્ટિપ્લેયર ગેમ્સ.  ઉદાહરણ તરીકે, જો તમે ફોન કૉલ પર છો અને થોડીક સેકંડ માટે રિસેપ્શન ગુમાવો છો, જ્યારે તમે ફરીથી કનેક્શન મેળવો છો, તો તમે કનેક્શન ગુમાવવા દરમિયાન શું બોલવામાં આવ્યું હતું તે સાંભળતા નથી.

### આખરી સુસંગતતા

લખ્યા પછી, વાંચન આખરે તેને જોશે (સામાન્ય રીતે મિલિસેકંડમાં).  ડેટા અસુમેળ રીતે નકલ કરવામાં આવે છે.

આ અભિગમ DNS અને ઇમેઇલ જેવી સિસ્ટમમાં જોવા મળે છે.  અત્યંત ઉપલબ્ધ સિસ્ટમોમાં અંતિમ સુસંગતતા સારી રીતે કામ કરે છે.

### મજબૂત સુસંગતતા

લખ્યા પછી, વાંચનારા તેને જોશે.  ડેટા સિંક્રનસ રીતે નકલ કરવામાં આવે છે.

આ અભિગમ ફાઇલ સિસ્ટમ્સ અને RDBMSes માં જોવા મળે છે.  ટ્રાન્ઝેક્શનની જરૂર હોય તેવી સિસ્ટમમાં મજબૂત સુસંગતતા સારી રીતે કામ કરે છે.

## ઉપલબ્ધતા પેટર્ન

ઉચ્ચ ઉપલબ્ધતાને સમર્થન આપવા માટે બે પૂરક દાખલાઓ છે: **ફેલ-ઓવર** અને **પ્રતિકૃતિ**.

### ફેલ-ઓવર

#### સક્રિય-નિષ્ક્રિય

સક્રિય-નિષ્ક્રિય નિષ્ફળતા સાથે, સ્ટેન્ડબાય પર સક્રિય અને નિષ્ક્રિય સર્વર વચ્ચે હૃદયના ધબકારા મોકલવામાં આવે છે.  જો હૃદયના ધબકારા અવરોધાય છે, તો નિષ્ક્રિય સર્વર સક્રિયનું IP સરનામું લઈ લે છે અને સેવા ફરી શરૂ કરે છે.

નિષ્ક્રિય સર્વર પહેલેથી જ 'હોટ' સ્ટેન્ડબાયમાં ચાલી રહ્યું છે અથવા તેને 'કોલ્ડ' સ્ટેન્ડબાયથી શરૂ કરવાની જરૂર છે કે કેમ તેના આધારે ડાઉનટાઇમની લંબાઈ નક્કી કરવામાં આવે છે.  માત્ર સક્રિય સર્વર ટ્રાફિકને હેન્ડલ કરે છે.

સક્રિય-નિષ્ક્રિય ફેલઓવરને માસ્ટર-સ્લેવ ફેલઓવર તરીકે પણ ઓળખવામાં આવે છે.

#### સક્રિય-સક્રિય

સક્રિય-સક્રિયમાં, બંને સર્વર ટ્રાફિકનું સંચાલન કરે છે, તેમની વચ્ચેનો ભાર ફેલાવે છે.

જો સર્વર્સ સાર્વજનિક છે, તો DNS ને બંને સર્વરના સાર્વજનિક IP વિશે જાણવાની જરૂર પડશે.  જો સર્વર્સ આંતરિક-સામનો હોય, તો એપ્લિકેશન તર્કને બંને સર્વર્સ વિશે જાણવાની જરૂર પડશે.

સક્રિય-સક્રિય ફેલઓવરને માસ્ટર-માસ્ટર ફેલઓવર તરીકે પણ ઓળખવામાં આવે છે.

### ગેરલાભ(ઓ): નિષ્ફળતા

* ફેલ-ઓવર વધુ હાર્ડવેર અને વધારાની જટિલતા ઉમેરે છે.
* જો કોઈ નવા લખેલા ડેટાને નિષ્ક્રિયમાં નકલ કરી શકાય તે પહેલાં સક્રિય સિસ્ટમ નિષ્ફળ જાય તો ડેટા ગુમાવવાની સંભાવના છે.

### સંખ્યામાં ઉપલબ્ધતા

ઉપલબ્ધતા ઘણીવાર અપટાઇમ (અથવા ડાઉનટાઇમ) દ્વારા સેવા ઉપલબ્ધ હોય તે સમયની ટકાવારી તરીકે માપવામાં આવે છે.  પ્રાપ્યતા સામાન્ય રીતે 9s ની ​​સંખ્યામાં માપવામાં આવે છે-- 99.99% ઉપલબ્ધતા ધરાવતી સેવાને ચાર 9s તરીકે વર્ણવવામાં આવે છે.

#### 99.9% ઉપલબ્ધતા - ત્રણ 9s

| અવધિ | સ્વીકાર્ય ડાઉનટાઇમ|
|------------------------------------------------------------ |
| દર વર્ષે ડાઉનટાઇમ | 8 કલાક 45 મિનિટ 57 સે |
| દર મહિને ડાઉનટાઇમ | 43m 49.7s |
| દર અઠવાડિયે ડાઉનટાઇમ | 10m 4.8s |
| દિવસ દીઠ ડાઉનટાઇમ | 1m 26.4s |

#### 99.99% ઉપલબ્ધતા - ચાર 9 સે

| અવધિ | સ્વીકાર્ય ડાઉનટાઇમ|
|------------------------------------------------------------ |
| દર વર્ષે ડાઉનટાઇમ | 52 મિનિટ 35.7 સેકન્ડ |
| દર મહિને ડાઉનટાઇમ | 4m 23s |
| દર અઠવાડિયે ડાઉનટાઇમ | 1 મી 5 સે |
| દિવસ દીઠ ડાઉનટાઇમ | 8.6 સેકન્ડ |

#### સમાંતર વિ ક્રમમાં ઉપલબ્ધતા

જો કોઈ સેવામાં નિષ્ફળતાની સંભાવના ધરાવતા બહુવિધ ઘટકોનો સમાવેશ થાય છે, તો સેવાની એકંદર ઉપલબ્ધતા ઘટકો અનુક્રમમાં છે કે સમાંતર છે તેના પર આધાર રાખે છે.

###### ક્રમમાં

જ્યારે ઉપલબ્ધતા < 100% સાથેના બે ઘટકો અનુક્રમમાં હોય ત્યારે એકંદરે ઉપલબ્ધતા ઘટે છે:

```
Availability (Total) = Availability (Foo) * Availability (Bar)
```

જો `Foo` અને `બાર` બંનેમાં 99.9% ઉપલબ્ધતા હોય, તો ક્રમમાં તેમની કુલ ઉપલબ્ધતા 99.8% હશે.

###### સમાંતર

જ્યારે ઉપલબ્ધતા < 100% સાથેના બે ઘટકો સમાંતર હોય ત્યારે એકંદરે ઉપલબ્ધતા વધે છે:

```
Availability (Total) = 1 - (1 - Availability (Foo)) * (1 - Availability (Bar))
```

જો `Foo` અને `બાર` બંનેમાં 99.9% ઉપલબ્ધતા હોય, તો સમાંતરમાં તેમની કુલ ઉપલબ્ધતા 99.9999% હશે.

## ડોમેન નેમ સિસ્ટમ

ડોમેન નેમ સિસ્ટમ (DNS) ડોમેન નામનો અનુવાદ કરે છે જેમ કે www.example.com IP એડ્રેસમાં.

ટોચના સ્તર પર થોડા અધિકૃત સર્વર્સ સાથે, DNS વંશવેલો છે.  તમારું રાઉટર અથવા ISP લુકઅપ કરતી વખતે કયા DNS સર્વરનો સંપર્ક કરવો તેની માહિતી પ્રદાન કરે છે.  નીચલા સ્તરના DNS સર્વર્સ કેશ મેપિંગ્સ, જે DNS પ્રચાર વિલંબને કારણે વાસી બની શકે છે.  DNS પરિણામો તમારા બ્રાઉઝર અથવા OS દ્વારા ચોક્કસ સમયગાળા માટે કેશ કરી શકાય છે, જે [ટાઈમ ટુ લાઈવ (TTL)](https://en.wikipedia.org/wiki/Time_to_live) દ્વારા નિર્ધારિત કરવામાં આવે છે.

* **NS રેકોર્ડ (નામ સર્વર)** - તમારા ડોમેન/સબડોમેઇન માટે DNS સર્વર્સનો ઉલ્લેખ કરે છે.
* **MX રેકોર્ડ (મેલ એક્સચેન્જ)** - સંદેશા સ્વીકારવા માટે મેલ સર્વર્સનો ઉલ્લેખ કરે છે.
* **એક રેકોર્ડ (સરનામું)** - IP સરનામા પર નામ દર્શાવે છે.
* **CNAME (પ્રમાણિક)** - નામ બીજા નામ અથવા `CNAME` (example.com થી www.example.com) અથવા `A` રેકોર્ડ તરફ નિર્દેશ કરે છે.

[CloudFlare](https://www.cloudflare.com/dns/) અને [Route 53](https://aws.amazon.com/route53/) જેવી સેવાઓ વ્યવસ્થાપિત DNS સેવાઓ પ્રદાન કરે છે.  કેટલીક DNS સેવાઓ વિવિધ પદ્ધતિઓ દ્વારા ટ્રાફિકને રૂટ કરી શકે છે:

* [ભારિત રાઉન્ડ રોબિન](https://www.jscape.com/blog/load-balancing-algorithms)
    * ટ્રાફિકને જાળવણી હેઠળના સર્વર પર જતા અટકાવો
    * વિવિધ ક્લસ્ટર કદ વચ્ચે સંતુલન
    * A/B પરીક્ષણ
* [લેટન્સી-આધારિત](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-latency.html)
* [ભૌગોલિક સ્થાન-આધારિત](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-geo.html)

### ગેરલાભ(ઓ): DNS

* DNS સર્વરને ઍક્સેસ કરવાથી થોડો વિલંબ થાય છે, જો કે ઉપર વર્ણવેલ કેશીંગ દ્વારા ઘટાડી શકાય છે.
* DNS સર્વર મેનેજમેન્ટ જટિલ હોઈ શકે છે અને સામાન્ય રીતે [સરકાર, ISPs અને મોટી કંપનીઓ] દ્વારા સંચાલિત થાય છે (http://superuser.com/questions/472695/who-controls-the-dns-servers/472729).
* DNS સેવાઓ તાજેતરમાં [DDoS હુમલા](http://dyn.com/blog/dyn-analysis-summary-of-friday-october-21-attack/) હેઠળ આવી છે, જે વપરાશકર્તાઓને Twitterના IP સરનામા(ઓ)ને જાણ્યા વિના Twitter જેવી વેબસાઇટ્સ ઍક્સેસ કરવાથી અટકાવે છે.

કન્ટેન્ટ ડિલિવરી નેટવર્ક (CDN) એ પ્રોક્સી સર્વર્સનું વૈશ્વિક સ્તરે વિતરિત નેટવર્ક છે, જે વપરાશકર્તાની નજીકના સ્થાનો પરથી સામગ્રી પ્રદાન કરે છે.  સામાન્ય રીતે, એચટીએમએલ/સીએસએસ/જેએસ, ફોટા અને વિડિયો જેવી સ્થિર ફાઇલો સીડીએનમાંથી આપવામાં આવે છે, જોકે એમેઝોનના ક્લાઉડફ્રન્ટ જેવા કેટલાક સીડીએન ગતિશીલ સામગ્રીને સપોર્ટ કરે છે.  સાઇટનું DNS રિઝોલ્યુશન ક્લાયન્ટને જણાવશે કે કયા સર્વરનો સંપર્ક કરવો.

CDN માંથી સામગ્રી પીરસવાથી બે રીતે પ્રભાવમાં નોંધપાત્ર સુધારો થઈ શકે છે:

* વપરાશકર્તાઓ તેમની નજીકના ડેટા કેન્દ્રોમાંથી સામગ્રી મેળવે છે
* તમારા સર્વર્સને વિનંતીઓ પૂરી કરવાની જરૂર નથી કે જે CDN પૂરી કરે

### પુશ સીડીએન

જ્યારે પણ તમારા સર્વર પર ફેરફારો થાય ત્યારે પુશ સીડીએન નવી સામગ્રી મેળવે છે.  તમે સામગ્રી પ્રદાન કરવા, સીડીએન પર સીધું અપલોડ કરવા અને સીડીએન તરફ નિર્દેશ કરવા માટે URL ને ફરીથી લખવાની સંપૂર્ણ જવાબદારી લો છો.  સામગ્રી ક્યારે સમાપ્ત થાય છે અને ક્યારે અપડેટ થાય છે તે તમે ગોઠવી શકો છો.  સામગ્રી ફક્ત ત્યારે જ અપલોડ કરવામાં આવે છે જ્યારે તે નવી અથવા બદલાયેલ હોય, ટ્રાફિકને ઓછો કરે છે, પરંતુ મહત્તમ સ્ટોરેજ કરે છે.

થોડી માત્રામાં ટ્રાફિક ધરાવતી સાઇટ્સ અથવા સામગ્રી સાથેની સાઇટ્સ કે જે ઘણીવાર અપડેટ થતી નથી તે પુશ CDN સાથે સારી રીતે કામ કરે છે.  નિયમિત સમયાંતરે પુનઃ ખેંચવાને બદલે સામગ્રી CDN પર એકવાર મૂકવામાં આવે છે.

### CDN ને ખેંચો

જ્યારે પ્રથમ વપરાશકર્તા સામગ્રીની વિનંતી કરે ત્યારે પુલ CDN તમારા સર્વરમાંથી નવી સામગ્રીને પકડે છે.  તમે તમારા સર્વર પર સામગ્રી છોડી દો અને CDN તરફ નિર્દેશ કરવા માટે URL ને ફરીથી લખો.  CDN પર કન્ટેન્ટ કેશ ન થાય ત્યાં સુધી આ ધીમી વિનંતીમાં પરિણમે છે.

એ [ટાઈમ-ટુ-લાઈવ (TTL)](https://en.wikipedia.org/wiki/Time_to_live) નક્કી કરે છે કે સામગ્રી કેટલો સમય કેશ કરવામાં આવે છે.  પુલ CDNs CDN પર સ્ટોરેજ સ્પેસ ઘટાડે છે, પરંતુ જો ફાઇલોની સમયસીમા સમાપ્ત થઈ જાય અને તે વાસ્તવમાં બદલાઈ જાય તે પહેલાં ખેંચાઈ જાય તો તે બિનજરૂરી ટ્રાફિક બનાવી શકે છે.

ભારે ટ્રાફિક ધરાવતી સાઇટ્સ પુલ CDN સાથે સારી રીતે કામ કરે છે, કારણ કે CDN પર માત્ર તાજેતરમાં જ વિનંતી કરાયેલ સામગ્રી સાથે ટ્રાફિક વધુ સમાનરૂપે ફેલાય છે.

### ગેરલાભ(ઓ): CDN

* ટ્રાફિકના આધારે સીડીએન ખર્ચ નોંધપાત્ર હોઈ શકે છે, જો કે આને વધારાના ખર્ચ સાથે તોલવું જોઈએ જે તમે સીડીએનનો ઉપયોગ ન કરો છો.
* જો સામગ્રી TTL સમાપ્ત થાય તે પહેલાં અપડેટ કરવામાં આવે તો તે વાસી હોઈ શકે છે.
* CDN ને CDN તરફ નિર્દેશ કરવા માટે સ્થિર સામગ્રી માટે URL બદલવાની જરૂર છે.

## લોડ બેલેન્સર

<p align="center">
  <img src="images/h81n9iK.png">
  <br/>
  <i><a href=http://horicky.blogspot.com/2010/10/scalable-system-design-patterns.html>Source: Scalable system design patterns</a></i>
</p>

લોડ બેલેન્સર્સ એપ્લીકેશન સર્વર્સ અને ડેટાબેસેસ જેવા કમ્પ્યુટિંગ સંસાધનોને ઇનકમિંગ ક્લાયન્ટ વિનંતીઓનું વિતરણ કરે છે.  દરેક કિસ્સામાં, લોડ બેલેન્સર કમ્પ્યુટિંગ સંસાધનમાંથી યોગ્ય ક્લાયન્ટને પ્રતિસાદ આપે છે.  લોડ બેલેન્સર અસરકારક છે:

* બિનઆરોગ્યપ્રદ સર્વર પર જવાની વિનંતીઓને અટકાવવી
* ઓવરલોડિંગ સંસાધનોને અટકાવવું
* નિષ્ફળતાના એક બિંદુને દૂર કરવામાં મદદ કરવી

લોડ બેલેન્સર્સને હાર્ડવેર (ખર્ચાળ) સાથે અથવા HAProxy જેવા સોફ્ટવેર સાથે લાગુ કરી શકાય છે.

વધારાના ફાયદાઓમાં શામેલ છે:

* **SSL સમાપ્તિ** - ઇનકમિંગ વિનંતીઓને ડિક્રિપ્ટ કરો અને સર્વર પ્રતિસાદોને એન્ક્રિપ્ટ કરો જેથી બેકએન્ડ સર્વર્સે આ સંભવિત ખર્ચાળ કામગીરી કરવાની જરૂર નથી
    * દરેક સર્વર પર [X.509 પ્રમાણપત્રો](https://en.wikipedia.org/wiki/X.509) ઇન્સ્ટોલ કરવાની જરૂરિયાતને દૂર કરે છે
* **સત્રની નિરંતરતા** - જો વેબ એપ્સ સત્રોનો ટ્રૅક રાખતી ન હોય તો કૂકીઝ ઇશ્યૂ કરો અને ચોક્કસ ક્લાયન્ટની વિનંતીઓને તે જ ઉદાહરણ પર રૂટ કરો

નિષ્ફળતાઓ સામે રક્ષણ આપવા માટે, [સક્રિય-નિષ્ક્રિય](#સક્રિય-નિષ્ક્રિય) અથવા [સક્રિય-સક્રિય](#સક્રિય-સક્રિય) મોડમાં, બહુવિધ લોડ બેલેન્સર સેટ કરવું સામાન્ય છે.

લોડ બેલેન્સર વિવિધ મેટ્રિક્સના આધારે ટ્રાફિકને રૂટ કરી શકે છે, જેમાં નીચેનાનો સમાવેશ થાય છે:

* રેન્ડમ
* ઓછામાં ઓછું લોડ
* સત્ર/કુકીઝ
* [રાઉન્ડ રોબિન અથવા વેઇટેડ રાઉન્ડ રોબિન](https://www.g33kinfo.com/info/round-robin-vs-weighted-round-robin-lb)
* [લેયર 4](#લેયર-4-લોડ-બેલેન્સિંગ)
* [લેયર 7](#લેયર-7-લોડ-બેલેન્સિંગ)

### લેયર 4 લોડ બેલેન્સિંગ

લેયર 4 લોડ બેલેન્સર્સ વિનંતીઓનું વિતરણ કેવી રીતે કરવું તે નક્કી કરવા માટે [ટ્રાન્સપોર્ટ લેયર](#કોમ્યુનિકેશન) પરની માહિતી જુએ છે.  સામાન્ય રીતે, આમાં હેડરમાં સ્ત્રોત, ગંતવ્ય IP સરનામાં અને પોર્ટનો સમાવેશ થાય છે, પરંતુ પેકેટની સામગ્રીનો સમાવેશ થતો નથી.  લેયર 4 લોડ બેલેન્સર્સ [નેટવર્ક એડ્રેસ ટ્રાન્સલેશન (NAT)](https://web.archive.org/web/20240117134735/https://www.nginx.com/resources/glossary/layer-4-load-balancing/) પરફોર્મ કરીને અપસ્ટ્રીમ સર્વર પર અને ત્યાંથી નેટવર્ક પેકેટ્સ ફોરવર્ડ કરે છે.

### લેયર 7 લોડ બેલેન્સિંગ

લેયર 7 લોડ બેલેન્સર્સ વિનંતીઓનું વિતરણ કેવી રીતે કરવું તે નક્કી કરવા માટે [એપ્લિકેશન લેયર](#communication) ને જુએ છે.  આમાં હેડર, સંદેશ અને કૂકીઝની સામગ્રી શામેલ હોઈ શકે છે.  લેયર 7 લોડ બેલેન્સર્સ નેટવર્ક ટ્રાફિકને સમાપ્ત કરે છે, સંદેશ વાંચે છે, લોડ-બેલેન્સિંગ નિર્ણય લે છે, પછી પસંદ કરેલ સર્વર સાથે કનેક્શન ખોલે છે.  ઉદાહરણ તરીકે, લેયર 7 લોડ બેલેન્સર વિડિયો ટ્રાફિકને એવા સર્વર્સ પર ડાયરેક્ટ કરી શકે છે જે વિડિયો હોસ્ટ કરે છે જ્યારે વધુ સંવેદનશીલ યુઝર બિલિંગ ટ્રાફિકને સુરક્ષા-કઠણ સર્વર્સ પર નિર્દેશિત કરે છે.

લવચીકતાના ખર્ચે, લેયર 4 લોડ બેલેન્સિંગ માટે લેયર 7 કરતાં ઓછો સમય અને કમ્પ્યુટિંગ સંસાધનોની જરૂર પડે છે, જો કે આધુનિક કોમોડિટી હાર્ડવેર પર પ્રભાવની અસર ન્યૂનતમ હોઈ શકે છે.

### આડું સ્કેલિંગ

લોડ બેલેન્સર્સ આડી સ્કેલિંગમાં પણ મદદ કરી શકે છે, પ્રદર્શન અને ઉપલબ્ધતામાં સુધારો કરી શકે છે.  કોમોડિટી મશીનોનો ઉપયોગ કરીને સ્કેલિંગ આઉટ વધુ ખર્ચાળ છે અને વધુ ખર્ચાળ હાર્ડવેર પર સિંગલ સર્વરને સ્કેલિંગ કરતાં વધુ ઉપલબ્ધતામાં પરિણમે છે, જેને **વર્ટિકલ સ્કેલિંગ** કહેવાય છે.  કોમોડિટી હાર્ડવેર પર કામ કરતી પ્રતિભાને ખાસ એન્ટરપ્રાઇઝ સિસ્ટમ્સ કરતાં ભાડે લેવી પણ સરળ છે.

#### ગેરલાભ(ઓ): હોરીઝોન્ટલ સ્કેલિંગ

* આડું સ્કેલિંગ જટિલતાનો પરિચય આપે છે અને તેમાં સર્વર્સનું ક્લોનિંગ સામેલ છે
    * સર્વર્સ સ્ટેટલેસ હોવા જોઈએ: તેમાં સત્રો અથવા પ્રોફાઇલ ચિત્રો જેવા કોઈપણ વપરાશકર્તા-સંબંધિત ડેટા ન હોવા જોઈએ
    * સત્રોને કેન્દ્રિય ડેટા સ્ટોરમાં સંગ્રહિત કરી શકાય છે જેમ કે [ડેટાબેઝ](#ડેટાબેઝ) (SQL, NoSQL) અથવા પર્સિસ્ટન્ટ [કેશ](#કેશ) (રેડીસ, મેમકેશ્ડ)
* ડાઉનસ્ટ્રીમ સર્વર્સ જેમ કે કેશ અને ડેટાબેઝને અપસ્ટ્રીમ સર્વર્સ સ્કેલ આઉટ થતાં વધુ એક સાથે જોડાણો હેન્ડલ કરવાની જરૂર છે

### ગેરલાભ(ઓ): લોડ બેલેન્સર

* લોડ બેલેન્સર પરફોર્મન્સ બોટલનેક બની શકે છે જો તેની પાસે પૂરતા સંસાધનો ન હોય અથવા જો તે યોગ્ય રીતે ગોઠવાયેલ ન હોય.
* નિષ્ફળતાના એક બિંદુને દૂર કરવામાં મદદ કરવા માટે લોડ બેલેન્સર રજૂ કરવાથી જટિલતા વધે છે.
* સિંગલ લોડ બેલેન્સર એ નિષ્ફળતાનો એક બિંદુ છે, બહુવિધ લોડ બેલેન્સરને ગોઠવવાથી જટિલતા વધે છે.

## રિવર્સ પ્રોક્સી (વેબ સર્વર)

<p align="center">
  <img src="images/n41Azff.png">
  <br/>
  <i><a href=https://upload.wikimedia.org/wikipedia/commons/6/67/Reverse_proxy_h2g2bob.svg>Source: Wikipedia</a></i>

રિવર્સ પ્રોક્સી એ વેબ સર્વર છે જે આંતરિક સેવાઓને કેન્દ્રિય બનાવે છે અને લોકોને એકીકૃત ઇન્ટરફેસ પ્રદાન કરે છે.  ક્લાયન્ટની વિનંતીઓ સર્વર પર ફોરવર્ડ કરવામાં આવે છે જે રિવર્સ પ્રોક્સી ક્લાયંટને સર્વરનો પ્રતિસાદ આપે તે પહેલાં તેને પૂર્ણ કરી શકે છે.

વધારાના ફાયદાઓમાં શામેલ છે:

* **સુરક્ષામાં વધારો** - બેકએન્ડ સર્વર્સ, બ્લેકલિસ્ટ IP, ક્લાયન્ટ દીઠ કનેક્શન્સની મર્યાદા સંખ્યા વિશે માહિતી છુપાવો
* **વધેલી માપનીયતા અને સુગમતા** - ક્લાઈન્ટો માત્ર રિવર્સ પ્રોક્સીનો આઈપી જુએ છે, જેનાથી તમે સર્વરને સ્કેલ કરી શકો છો અથવા તેમનું રૂપરેખાંકન બદલી શકો છો
* **SSL સમાપ્તિ** - ઇનકમિંગ વિનંતીઓને ડિક્રિપ્ટ કરો અને સર્વર પ્રતિસાદોને એન્ક્રિપ્ટ કરો જેથી બેકએન્ડ સર્વર્સે આ સંભવિત ખર્ચાળ કામગીરી કરવાની જરૂર નથી
    * દરેક સર્વર પર [X.509 પ્રમાણપત્રો](https://en.wikipedia.org/wiki/X.509) ઇન્સ્ટોલ કરવાની જરૂરિયાતને દૂર કરે છે
* **કમ્પ્રેશન** - સર્વર પ્રતિસાદોને સંકુચિત કરો
* **કેશિંગ** - કેશ્ડ વિનંતીઓ માટે પ્રતિસાદ પરત કરો
* **સ્થિર સામગ્રી** - સ્થિર સામગ્રી સીધી સર્વ કરો
    * HTML/CSS/JS
    * ફોટા
    * વિડિઓઝ
    *વગેરે

### લોડ બેલેન્સર વિ રિવર્સ પ્રોક્સી

જ્યારે તમારી પાસે બહુવિધ સર્વર હોય ત્યારે લોડ બેલેન્સર જમાવવું ઉપયોગી છે.  મોટે ભાગે, લોડ બેલેન્સર ટ્રાફિકને સમાન કાર્યને સેવા આપતા સર્વર્સના સમૂહ પર લઈ જાય છે.
* રિવર્સ પ્રોક્સી માત્ર એક વેબ સર્વર અથવા એપ્લિકેશન સર્વર સાથે પણ ઉપયોગી થઈ શકે છે, જે અગાઉના વિભાગમાં વર્ણવેલ લાભો ખોલે છે.
* NGINX અને HAProxy જેવા સોલ્યુશન્સ લેયર 7 રિવર્સ પ્રોક્સી અને લોડ બેલેન્સિંગ બંનેને સપોર્ટ કરી શકે છે.

### ગેરલાભ(ઓ): રિવર્સ પ્રોક્સી

* રિવર્સ પ્રોક્સી રજૂ કરવાથી જટિલતા વધે છે.
* સિંગલ રિવર્સ પ્રોક્સી એ નિષ્ફળતાનો એક બિંદુ છે, જે બહુવિધ રિવર્સ પ્રોક્સીને ગોઠવે છે (એટલે ​​કે [failover](https://en.wikipedia.org/wiki/Failover)) વધુ જટિલતા વધારે છે.

## એપ્લિકેશન સ્તર

વેબ લેયરને એપ્લીકેશન લેયર (પ્લેટફોર્મ લેયર તરીકે પણ ઓળખાય છે) થી અલગ કરવાથી તમે બંને સ્તરોને સ્વતંત્ર રીતે માપવા અને ગોઠવી શકો છો.  એક નવું API ઉમેરવાનું પરિણામ એપ્લીકેશન સર્વર્સ ઉમેરવામાં આવે છે, જેમાં વધારાના વેબ સર્વર્સ ઉમેર્યા વગર જરૂરી છે.  **એક જવાબદારી સિદ્ધાંત** નાની અને સ્વાયત્ત સેવાઓ માટે હિમાયત કરે છે જે એકસાથે કામ કરે છે.  નાની સેવાઓ ધરાવતી નાની ટીમો ઝડપી વૃદ્ધિ માટે વધુ આક્રમક રીતે આયોજન કરી શકે છે.

એપ્લીકેશન લેયરમાં કામદારો પણ [અસિંક્રોનિઝમ](#અસિંક્રોનિઝમ) સક્ષમ કરવામાં મદદ કરે છે.

Each service runs a unique process and communicates through a well-defined, lightweight mechanism to serve a business goal. <sup><a href=https://smartbear.com/learn/api-design/what-are-microservices>1</a></sup>

Pinterest, ઉદાહરણ તરીકે, નીચેની માઇક્રોસેવાઓ હોઈ શકે છે: વપરાશકર્તા પ્રોફાઇલ, અનુયાયી, ફીડ, શોધ, ફોટો અપલોડ, વગેરે.

  <img src="images/Xkm5CXz.png">

### રિલેશનલ ડેટાબેઝ મેનેજમેન્ટ સિસ્ટમ (RDBMS)

રિલેશનલ ડેટાબેઝ જેમ કે SQL એ કોષ્ટકોમાં ગોઠવાયેલ ડેટા વસ્તુઓનો સંગ્રહ છે.

**ACID** એ રિલેશનલ ડેટાબેઝ [ટ્રાન્ઝેક્શન્સ](https://en.wikipedia.org/wiki/Database_transaction) ના ગુણધર્મોનો સમૂહ છે.

* **પરમાણુતા** - દરેક વ્યવહાર બધો અથવા કંઈ નથી
* **સંગતતા** - કોઈપણ વ્યવહાર ડેટાબેઝને એક માન્ય રાજ્યમાંથી બીજી સ્થિતિમાં લાવશે
* **અલગતા** - વ્યવહારો એકસાથે એક્ઝિક્યુટ કરવાથી તે જ પરિણામો આવે છે જેમ કે વ્યવહારો સીરીયલ રીતે ચલાવવામાં આવ્યા હોય
* **ટકાઉપણું** - એકવાર વ્યવહાર થઈ જાય, તે યથાવત્ રહેશે

રિલેશનલ ડેટાબેઝને માપવા માટે ઘણી તકનીકો છે: **માસ્ટર-સ્લેવ રેપ્લિકેશન**, **માસ્ટર-માસ્ટર રેપ્લિકેશન**, **ફેડરેશન**, **શાર્ડિંગ**, **ડિનોર્મલાઈઝેશન** અને **એસક્યુએલ ટ્યુનિંગ**.

#### માસ્ટર-સ્લેવ પ્રતિકૃતિ

માસ્ટર વાંચવા અને લખવાની સેવા આપે છે, એક અથવા વધુ ગુલામોને લખાણોની નકલ કરે છે, જે ફક્ત વાંચન જ સેવા આપે છે.  ગુલામો વૃક્ષ જેવી ફેશનમાં વધારાના ગુલામોની નકલ પણ કરી શકે છે.  જો માસ્ટર ઑફલાઇન થઈ જાય, તો જ્યાં સુધી ગુલામને માસ્ટર તરીકે બઢતી આપવામાં ન આવે અથવા નવા માસ્ટરની જોગવાઈ કરવામાં ન આવે ત્યાં સુધી સિસ્ટમ ફક્ત-વાંચવા માટેના મોડમાં કામ કરવાનું ચાલુ રાખી શકે છે.

##### ગેરલાભ(ઓ): માસ્ટર-સ્લેવ પ્રતિકૃતિ

* ગુલામને માસ્ટર બનાવવા માટે વધારાના તર્કની જરૂર છે.
* **માસ્ટર-સ્લેવ અને માસ્ટર-માસ્ટર બંને સાથે સંબંધિત મુદ્દાઓ માટે [ગેરલાભ(ઓ): પ્રતિકૃતિ](#ગેરફાયદા-પ્રતિકૃતિ) જુઓ.

#### માસ્ટર-માસ્ટર પ્રતિકૃતિ

બંને માસ્ટર્સ વાંચન અને લેખન આપે છે અને લેખન પર એકબીજા સાથે સંકલન કરે છે.  જો બેમાંથી એક માસ્ટર નીચે જાય, તો સિસ્ટમ વાંચવા અને લખવા બંને સાથે કામ કરવાનું ચાલુ રાખી શકે છે.

##### ગેરલાભ(ઓ): માસ્ટર-માસ્ટર પ્રતિકૃતિ

* તમારે લોડ બેલેન્સરની જરૂર પડશે અથવા ક્યાં લખવું તે નક્કી કરવા માટે તમારે તમારા એપ્લિકેશન લોજિકમાં ફેરફાર કરવાની જરૂર પડશે.
* મોટાભાગની માસ્ટર-માસ્ટર સિસ્ટમ્સ કાં તો ઢીલી રીતે સુસંગત હોય છે (ACIDનું ઉલ્લંઘન કરતી હોય છે) અથવા સિંક્રોનાઇઝેશનને કારણે લખવાની વિલંબમાં વધારો થયો છે.
* જેમ જેમ વધુ લખવાના નોડ્સ ઉમેરવામાં આવે છે અને વિલંબિતતા વધે છે તેમ સંઘર્ષનું નિરાકરણ વધુ અમલમાં આવે છે.
* **માસ્ટર-સ્લેવ અને માસ્ટર-માસ્ટર બંને સાથે સંબંધિત મુદ્દાઓ માટે [ગેરલાભ(ઓ): પ્રતિકૃતિ](#ગેરફાયદા-પ્રતિકૃતિ) જુઓ.

##### ગેરલાભ(ઓ): નકલ

* જો કોઈ નવા લખેલા ડેટાને અન્ય નોડ્સ પર નકલ કરી શકાય તે પહેલાં માસ્ટર નિષ્ફળ જાય તો ડેટા ગુમાવવાની સંભાવના છે.
* લખાણો વાંચેલી પ્રતિકૃતિઓ પર ફરીથી ચલાવવામાં આવે છે.  જો ત્યાં ઘણા બધા લખાણો હોય, તો વાંચેલી પ્રતિકૃતિઓ ફરીથી ચલાવવામાં આવતા લખાણો સાથે અટવાઈ શકે છે અને તેટલા વાંચન કરી શકતા નથી.
* જેટલા વધુ વાંચેલા ગુલામો, તેટલી વધુ તમારે નકલ કરવી પડશે, જે વધુ પ્રતિકૃતિ લેગ તરફ દોરી જાય છે.
* કેટલીક સિસ્ટમો પર, માસ્ટરને લખવાથી સમાંતર લખવા માટે બહુવિધ થ્રેડો પેદા થઈ શકે છે, જ્યારે રીડ પ્રતિકૃતિઓ માત્ર એક થ્રેડ સાથે ક્રમિક રીતે લખવાનું સમર્થન કરે છે.
* પ્રતિકૃતિ વધુ હાર્ડવેર અને વધારાની જટિલતા ઉમેરે છે.

#### ફેડરેશન

<p align="center">
  <img src="images/U3qV33e.png">
  <br/>

ફેડરેશન (અથવા ફંક્શનલ પાર્ટીશનીંગ) ડેટાબેઝને ફંક્શન દ્વારા વિભાજિત કરે છે.  ઉદાહરણ તરીકે, એકલ, મોનોલિથિક ડેટાબેઝને બદલે, તમારી પાસે ત્રણ ડેટાબેઝ હોઈ શકે છે: **ફોરમ**, **વપરાશકર્તા** અને **ઉત્પાદનો**, જેના પરિણામે દરેક ડેટાબેઝ પર ઓછો વાંચવા અને લખવાનો ટ્રાફિક આવે છે અને તેથી પ્રતિકૃતિમાં ઘટાડો થાય છે.  નાના ડેટાબેઝના પરિણામે મેમરીમાં ફિટ થઈ શકે તેવા વધુ ડેટા મળે છે, જે બદલામાં કેશ સ્થાનમાં સુધારો થવાને કારણે વધુ કેશ હિટમાં પરિણમે છે.  કોઈ એક સેન્ટ્રલ માસ્ટર સીરીયલાઈઝિંગ રાઈટ વગર તમે સમાંતર લખી શકો છો, થ્રુપુટ વધારી શકો છો.

##### ગેરલાભ(ઓ): ફેડરેશન

* જો તમારી સ્કીમાને વિશાળ કાર્યો અથવા કોષ્ટકોની જરૂર હોય તો ફેડરેશન અસરકારક નથી.
* કયા ડેટાબેઝને વાંચવા અને લખવા તે નક્કી કરવા માટે તમારે તમારા એપ્લિકેશન લોજિકને અપડેટ કરવાની જરૂર પડશે.
* [સર્વર લિંક] (http://stackoverflow.com/questions/5145637/querying-data-by-joining-two-tables-in-two-database-on-different-servers) સાથે બે ડેટાબેઝમાંથી ડેટા જોડાવું વધુ જટિલ છે.
* ફેડરેશન વધુ હાર્ડવેર અને વધારાની જટિલતા ઉમેરે છે.

#### શેરિંગ

<p align="center">
  <img src="images/wU8x5Id.png">
  <br/>
  <i><a href=http://www.slideshare.net/jboner/scalability-availability-stability-patterns/>Source: Scalability, availability, stability, patterns</a></i>
</p>

શેરિંગ વિવિધ ડેટાબેઝમાં ડેટાનું વિતરણ કરે છે જેમ કે દરેક ડેટાબેઝ ફક્ત ડેટાના સબસેટનું સંચાલન કરી શકે છે.  ઉદાહરણ તરીકે યુઝર્સ ડેટાબેઝ લેતાં, જેમ જેમ યુઝર્સની સંખ્યામાં વધારો થાય છે તેમ તેમ ક્લસ્ટરમાં વધુ શાર્ડ ઉમેરવામાં આવે છે.

[ફેડરેશન](#ફેડરેશન)ના ફાયદાઓની જેમ, શાર્ડિંગના પરિણામે ઓછા વાંચવા અને લખવાનો ટ્રાફિક, ઓછી નકલ અને વધુ કેશ હિટ થાય છે.  અનુક્રમણિકાનું કદ પણ ઓછું કરવામાં આવે છે, જે સામાન્ય રીતે ઝડપી પ્રશ્નો સાથે પ્રદર્શનમાં સુધારો કરે છે.  જો એક શાર્ડ નીચે જાય છે, તો અન્ય શાર્ડ હજુ પણ કાર્યરત છે, જો કે તમે ડેટાની ખોટ ટાળવા માટે અમુક પ્રકારની પ્રતિકૃતિ ઉમેરવા માંગો છો.  ફેડરેશનની જેમ, ત્યાં કોઈ એક સેન્ટ્રલ માસ્ટર સીરીયલાઈઝિંગ રાઈટ નથી, જે તમને વધેલા થ્રુપુટ સાથે સમાંતર લખવાની મંજૂરી આપે છે.

વપરાશકર્તાઓના કોષ્ટકને શાર્ડ કરવાની સામાન્ય રીતો ક્યાં તો વપરાશકર્તાના અંતિમ નામના પ્રારંભિક અથવા વપરાશકર્તાના ભૌગોલિક સ્થાન દ્વારા છે.

##### ગેરલાભ(ઓ): શાર્ડિંગ

* તમારે શાર્ડ્સ સાથે કામ કરવા માટે તમારા એપ્લિકેશન લોજિકને અપડેટ કરવાની જરૂર પડશે, જે જટિલ SQL ક્વેરીઝમાં પરિણમી શકે છે.
* ડેટાનું વિતરણ શાર્ડમાં એકતરફી બની શકે છે.  ઉદાહરણ તરીકે, શાર્ડ પર પાવર વપરાશકારોનો સમૂહ અન્યની સરખામણીમાં તે શાર્ડ પરનો ભાર વધારી શકે છે.
    * પુનઃસંતુલન વધારાની જટિલતા ઉમેરે છે.  [સતત હેશિંગ](http://www.paperplanes.de/2011/12/9/the-magic-of-consistent-hashing.html) પર આધારિત શાર્ડિંગ ફંક્શન ટ્રાન્સફર કરેલા ડેટાની માત્રા ઘટાડી શકે છે.
* બહુવિધ શાર્ડ્સમાંથી ડેટા જોડવો વધુ જટિલ છે.
* શાર્ડિંગ વધુ હાર્ડવેર અને વધારાની જટિલતા ઉમેરે છે.

#### ડિનોર્મલાઇઝેશન

ડિનોર્મલાઇઝેશન કેટલાક લેખન પ્રદર્શનના ખર્ચે વાંચન પ્રદર્શનને સુધારવાનો પ્રયાસ કરે છે.  ખર્ચાળ જોડાઓને ટાળવા માટે ડેટાની બિનજરૂરી નકલો બહુવિધ કોષ્ટકોમાં લખવામાં આવે છે.  કેટલાક RDBMS જેમ કે [PostgreSQL](https://en.wikipedia.org/wiki/PostgreSQL) અને Oracle સપોર્ટ [materialized views](https://en.wikipedia.org/wiki/Materialized_view) જે બિનજરૂરી માહિતી સંગ્રહિત કરવાનું અને બિનજરૂરી કોપને રાખવાનું કામ સંભાળે છે.

એકવાર ડેટા [ફેડરેશન](#ફેડરેશન) અને [શાર્ડિંગ](#શાર્ડિંગ) જેવી તકનીકો સાથે વિતરિત થઈ જાય, ત્યારે સમગ્ર ડેટા સેન્ટર્સમાં જોડાવાનું સંચાલન કરવું જટિલતામાં વધારો કરે છે.  ડિનોર્મલાઇઝેશન આવા જટિલ જોડાણોની જરૂરિયાતને અટકાવી શકે છે.

મોટાભાગની સિસ્ટમોમાં, વાંચન 100:1 અથવા તો 1000:1 લખવાની સંખ્યા કરતાં વધુ હોઈ શકે છે.  એક જટિલ ડેટાબેઝ જોઇનમાં પરિણમે છે તે વાંચન ખૂબ ખર્ચાળ હોઈ શકે છે, જે ડિસ્ક કામગીરી પર નોંધપાત્ર સમય વિતાવે છે.

##### ગેરલાભ(ઓ): ડીનોર્મલાઈઝેશન

* ડેટા ડુપ્લિકેટ છે.
* મર્યાદાઓ માહિતીની બિનજરૂરી નકલોને સમન્વયમાં રહેવામાં મદદ કરી શકે છે, જે ડેટાબેઝ ડિઝાઇનની જટિલતાને વધારે છે.
* ભારે લખાણના ભાર હેઠળ અસાધારણ ડેટાબેઝ તેના સામાન્યકૃત સમકક્ષ કરતાં વધુ ખરાબ પ્રદર્શન કરી શકે છે.

#### SQL ટ્યુનિંગ

SQL ટ્યુનિંગ એ એક વ્યાપક વિષય છે અને ઘણી [પુસ્તકો](https://www.amazon.com/s/ref=nb_sb_noss_2?url=search-alias%3Daps&field-keywords=sql+tuning) સંદર્ભ તરીકે લખવામાં આવી છે.

**બેન્ચમાર્ક** અને **પ્રોફાઈલ**નું અનુકરણ કરવા અને અવરોધોને ઉજાગર કરવા માટે મહત્વપૂર્ણ છે.

* **બેન્ચમાર્ક** - [ab](http://httpd.apache.org/docs/2.2/programs/ab.html) જેવા ટૂલ્સ વડે ઉચ્ચ-લોડ પરિસ્થિતિઓનું અનુકરણ કરો.
* **પ્રોફાઇલ** - પ્રદર્શન સમસ્યાઓને ટ્રૅક કરવામાં સહાય માટે [ધીમી ક્વેરી લૉગ](http://dev.mysql.com/doc/refman/5.7/en/slow-query-log.html) જેવા સાધનોને સક્ષમ કરો.

બેન્ચમાર્કિંગ અને પ્રોફાઇલિંગ તમને નીચેના ઑપ્ટિમાઇઝેશન તરફ નિર્દેશ કરી શકે છે.

##### સ્કીમાને સજ્જડ કરો

* ઝડપી ઍક્સેસ માટે સંલગ્ન બ્લોક્સમાં MySQL ડિસ્ક પર ડમ્પ કરે છે.
* ફિક્સ-લેન્થ ફીલ્ડ્સ માટે `VARCHAR` ને બદલે `CHAR` નો ઉપયોગ કરો.
    * `CHAR` અસરકારક રીતે ઝડપી, રેન્ડમ એક્સેસ માટે પરવાનગી આપે છે, જ્યારે `VARCHAR` સાથે, તમારે આગલી એક પર જતા પહેલા સ્ટ્રીંગનો અંત શોધવો પડશે.
* બ્લોગ પોસ્ટ્સ જેવા ટેક્સ્ટના મોટા બ્લોક્સ માટે `TEXT` નો ઉપયોગ કરો.  `TEXT` બુલિયન શોધ માટે પણ પરવાનગી આપે છે.  `ટેક્સ્ટ` ફીલ્ડનો ઉપયોગ કરવાથી ડિસ્ક પર પોઇન્ટર સંગ્રહિત થાય છે જેનો ઉપયોગ ટેક્સ્ટ બ્લોક શોધવા માટે થાય છે.
* 2^32 અથવા 4 બિલિયન સુધીની મોટી સંખ્યાઓ માટે `INT` નો ઉપયોગ કરો.
* ફ્લોટિંગ પોઈન્ટની રજૂઆતની ભૂલો ટાળવા માટે ચલણ માટે `દશમ' નો ઉપયોગ કરો.
* મોટા `બ્લોબ્સ` સ્ટોર કરવાનું ટાળો, તેના બદલે ઑબ્જેક્ટ ક્યાંથી મેળવવો તેનું સ્થાન સંગ્રહિત કરો.
* `VARCHAR(255)` એ અક્ષરોની સૌથી મોટી સંખ્યા છે જેને 8 બીટ નંબરમાં ગણી શકાય છે, જે ઘણીવાર અમુક RDBMSમાં બાઈટનો મહત્તમ ઉપયોગ કરે છે.
* જ્યાં લાગુ પડતું હોય ત્યાં `NOT NULL` અવરોધ સેટ કરો [શોધ પ્રદર્શનમાં સુધારો](http://stackoverflow.com/questions/1017239/how-do-null-values-affect-performance-in-a-database-search).

##### સારા સૂચકાંકોનો ઉપયોગ કરો

* તમે જે કૉલમ ક્વેરી કરી રહ્યાં છો (`પસંદ કરો`, `ગ્રુપ બાય`, `ઑર્ડર બાય`, `જોઇન`) સૂચકાંકો સાથે વધુ ઝડપી હોઈ શકે છે.
* સૂચકાંકોને સામાન્ય રીતે સ્વ-સંતુલિત [B-tree](https://en.wikipedia.org/wiki/B-tree) તરીકે રજૂ કરવામાં આવે છે જે ડેટાને સૉર્ટ રાખે છે અને લઘુગણક સમયમાં શોધ, અનુક્રમિક ઍક્સેસ, નિવેશ અને કાઢી નાખવાની મંજૂરી આપે છે.
* ઇન્ડેક્સ મૂકવાથી ડેટા મેમરીમાં રાખી શકાય છે, વધુ જગ્યાની જરૂર પડે છે.
* લખાણ પણ ધીમા હોઈ શકે છે કારણ કે ઇન્ડેક્સને પણ અપડેટ કરવાની જરૂર છે.
* મોટી માત્રામાં ડેટા લોડ કરતી વખતે, સૂચકાંકોને અક્ષમ કરવા, ડેટા લોડ કરવા, પછી સૂચકાંકોને ફરીથી બનાવવું વધુ ઝડપી હોઈ શકે છે.

### NoSQL

NoSQL એ **કી-વેલ્યુ સ્ટોર**, **દસ્તાવેજ સ્ટોર**, **વિશાળ કૉલમ સ્ટોર**, અથવા **ગ્રાફ ડેટાબેઝ**માં રજૂ કરાયેલ ડેટા વસ્તુઓનો સંગ્રહ છે.  ડેટા અસામાન્ય છે, અને જોડાઓ સામાન્ય રીતે એપ્લિકેશન કોડમાં કરવામાં આવે છે.  મોટાભાગના NoSQL સ્ટોર્સમાં સાચા ACID વ્યવહારોનો અભાવ હોય છે અને [અંતિમ સુસંગતતા](#eventual-consistency) તરફેણ કરતા હોય છે.

**BASE** નો ઉપયોગ વારંવાર NoSQL ડેટાબેઝના ગુણધર્મોને વર્ણવવા માટે થાય છે.  [CAP પ્રમેય](#cap-theorem) ની સરખામણીમાં, BASE સુસંગતતા પર ઉપલબ્ધતા પસંદ કરે છે.

* **મૂળભૂત રીતે ઉપલબ્ધ** - સિસ્ટમ ઉપલબ્ધતાની ખાતરી આપે છે.
* **સૉફ્ટ સ્ટેટ** - સિસ્ટમની સ્થિતિ સમય સાથે બદલાઈ શકે છે, ઇનપુટ વિના પણ.
* **આકસ્મિક સુસંગતતા** - તે સમયગાળા દરમિયાન સિસ્ટમ ઇનપુટ પ્રાપ્ત કરતી નથી તે જોતાં, સમયના સમયગાળામાં સિસ્ટમ સુસંગત બનશે.

[SQL અથવા NoSQL](#sql-or-nosql) વચ્ચે પસંદગી કરવા ઉપરાંત, તે સમજવામાં મદદરૂપ છે કે કયા પ્રકારનો NoSQL ડેટાબેઝ તમારા ઉપયોગના કેસ(કેસો) સાથે શ્રેષ્ઠ રીતે બંધબેસે છે.  અમે આગળના વિભાગમાં **કી-વેલ્યુ સ્ટોર**, **દસ્તાવેજ સ્ટોર**, **વિશાળ કૉલમ સ્ટોર** અને **ગ્રાફ ડેટાબેસેસ**ની સમીક્ષા કરીશું.

#### કી-વેલ્યુ સ્ટોર

> એબ્સ્ટ્રેક્શન: હેશ ટેબલ

કી-વેલ્યુ સ્ટોર સામાન્ય રીતે O(1) વાંચવા અને લખવા માટે પરવાનગી આપે છે અને ઘણીવાર મેમરી અથવા SSD દ્વારા સમર્થિત હોય છે.  ડેટા સ્ટોર્સ [લેક્સિકોગ્રાફિક ક્રમ](https://en.wikipedia.org/wiki/Lexicographical_order) માં કીને જાળવી શકે છે, જે કી રેન્જની કાર્યક્ષમ પુનઃપ્રાપ્તિની મંજૂરી આપે છે.  કી-વેલ્યુ સ્ટોર્સ મેટાડેટાને મૂલ્ય સાથે સ્ટોર કરવાની મંજૂરી આપી શકે છે.

કી-વેલ્યુ સ્ટોર્સ ઉચ્ચ પ્રદર્શન પ્રદાન કરે છે અને તેનો ઉપયોગ સામાન્ય ડેટા મોડલ અથવા ઝડપથી બદલાતા ડેટા માટે થાય છે, જેમ કે ઇન-મેમરી કેશ લેયર.  કારણ કે તેઓ ઓપરેશન્સનો માત્ર મર્યાદિત સેટ ઓફર કરે છે, જો વધારાની કામગીરીની જરૂર હોય તો જટિલતાને એપ્લિકેશન સ્તરમાં ખસેડવામાં આવે છે.

કી-વેલ્યુ સ્ટોર એ વધુ જટિલ સિસ્ટમો માટેનો આધાર છે જેમ કે દસ્તાવેજ સ્ટોર, અને કેટલાક કિસ્સાઓમાં, ગ્રાફ ડેટાબેઝ.

#### દસ્તાવેજની દુકાન

> એબ્સ્ટ્રેક્શન: મૂલ્યો તરીકે સંગ્રહિત દસ્તાવેજો સાથે કી-વેલ્યુ સ્ટોર

દસ્તાવેજ સ્ટોર દસ્તાવેજો (XML, JSON, દ્વિસંગી, વગેરે) ની આસપાસ કેન્દ્રિત છે, જ્યાં દસ્તાવેજ આપેલ ઑબ્જેક્ટ માટે તમામ માહિતી સંગ્રહિત કરે છે.  ડોક્યુમેન્ટ સ્ટોર્સ એપીઆઈ અથવા ક્વેરી લેંગ્વેજ આપે છે જે ડોક્યુમેન્ટની આંતરિક રચનાના આધારે ક્વેરી કરે છે.  *નોંધ, ઘણા કી-વેલ્યુ સ્ટોર્સમાં મૂલ્યના મેટાડેટા સાથે કામ કરવા માટેની સુવિધાઓનો સમાવેશ થાય છે, જે આ બે સ્ટોરેજ પ્રકારો વચ્ચેની રેખાઓને અસ્પષ્ટ કરે છે.*

અંતર્ગત અમલીકરણના આધારે, દસ્તાવેજો સંગ્રહ, ટૅગ્સ, મેટાડેટા અથવા ડિરેક્ટરીઓ દ્વારા ગોઠવવામાં આવે છે.  જો કે દસ્તાવેજોને એકસાથે સંગઠિત અથવા જૂથબદ્ધ કરી શકાય છે, દસ્તાવેજોમાં એવા ક્ષેત્રો હોઈ શકે છે જે એકબીજાથી સંપૂર્ણપણે અલગ હોય છે.

[MongoDB](https://www.mongodb.com/mongodb-architecture) અને [CouchDB](https://blog.couchdb.org/2016/08/01/couchdb-2-0-architecture/) જેવા કેટલાક દસ્તાવેજ સ્ટોર પણ જટિલ પ્રશ્નો કરવા માટે SQL જેવી ભાષા પ્રદાન કરે છે.  [DynamoDB](http://www.read.seas.harvard.edu/~kohler/class/cs239-w08/decandia07dynamo.pdf) કી-મૂલ્યો અને દસ્તાવેજો બંનેને સમર્થન આપે છે.

ડોક્યુમેન્ટ સ્ટોર્સ ઉચ્ચ સુગમતા પ્રદાન કરે છે અને તેનો ઉપયોગ વારંવાર બદલાતા ડેટા સાથે કામ કરવા માટે થાય છે.

#### વિશાળ કૉલમ સ્ટોર

<p align="center">
  <img src="images/n16iOGk.png">

> એબ્સ્ટ્રેક્શન: નેસ્ટેડ મેપ `કૉલમ ફેમિલી<રોકી, કૉલમ્સ<કોલકી, વેલ્યુ, ટાઇમસ્ટેમ્પ>>`

વિશાળ કૉલમ સ્ટોરનું ડેટાનું મૂળભૂત એકમ કૉલમ (નામ/મૂલ્ય જોડી) છે.  કૉલમને કૉલમ ફેમિલીમાં જૂથબદ્ધ કરી શકાય છે (SQL કોષ્ટકને અનુરૂપ).  સુપર કૉલમ પરિવારો આગળ જૂથ કૉલમ પરિવારો.  તમે દરેક કૉલમને પંક્તિ કી વડે સ્વતંત્ર રીતે ઍક્સેસ કરી શકો છો અને સમાન પંક્તિ કી સાથેના કૉલમ એક પંક્તિ બનાવે છે.  દરેક મૂલ્યમાં સંસ્કરણ અને સંઘર્ષના નિરાકરણ માટે ટાઇમસ્ટેમ્પ હોય છે.

Google એ પ્રથમ વિશાળ કૉલમ સ્ટોર તરીકે [Bigtable](http://www.read.seas.harvard.edu/~kohler/class/cs239-w08/chang06bigtable.pdf) રજૂ કર્યું, જેણે ઓપન-સોર્સ [HBase](https://www.edureka.co/blog/hbase-archites) અને ઘણી વાર Habase-archites-in-સ્રોતને પ્રભાવિત કર્યું. [Cassandra](http://docs.datastax.com/en/cassandra/3.0/cassandra/architecture/archIntro.html) Facebook તરફથી.  બિગટેબલ, એચબેઝ અને કેસાન્ડ્રા જેવા સ્ટોર્સ લેક્સિકોગ્રાફિક ક્રમમાં ચાવીઓ જાળવી રાખે છે, જે પસંદગીની કી શ્રેણીઓને કાર્યક્ષમ પુનઃપ્રાપ્તિની મંજૂરી આપે છે.

વિશાળ કૉલમ સ્ટોર્સ ઉચ્ચ ઉપલબ્ધતા અને ઉચ્ચ માપનીયતા પ્રદાન કરે છે.  તેઓ મોટાભાગે ખૂબ મોટા ડેટા સેટ માટે ઉપયોગમાં લેવાય છે.

ગ્રાફ ડેટાબેઝમાં, દરેક નોડ એક રેકોર્ડ છે અને દરેક ચાપ એ બે ગાંઠો વચ્ચેનો સંબંધ છે.  ગ્રાફ ડેટાબેઝને ઘણી વિદેશી કી અથવા ઘણા-થી-ઘણા સંબંધો સાથેના જટિલ સંબંધોને રજૂ કરવા માટે ઑપ્ટિમાઇઝ કરવામાં આવે છે.

### SQL અથવા NoSQL

<p align="center">
  <img src="images/wXGqG5f.png">
  <br/>
  <i><a href=https://www.infoq.com/articles/Transition-RDBMS-NoSQL/>Source: Transitioning from RDBMS to NoSQL</a></i>
</p>

**SQL** માટેનાં કારણો:

* સ્ટ્રક્ચર્ડ ડેટા
* કડક સ્કીમા
* રિલેશનલ ડેટા
* જટિલ જોડાવાની જરૂર છે
* વ્યવહારો
* સ્કેલિંગ માટે પેટર્ન સાફ કરો
* વધુ સ્થાપિત: વિકાસકર્તાઓ, સમુદાય, કોડ, સાધનો, વગેરે
* ઇન્ડેક્સ દ્વારા લુકઅપ ખૂબ જ ઝડપી છે

**NoSQL** માટેનાં કારણો:

* અર્ધ-સંરચિત ડેટા
* ડાયનેમિક અથવા લવચીક સ્કીમા
* બિન-સંબંધિત ડેટા
* જટિલ જોડાવાની જરૂર નથી
* ઘણા ટીબી (અથવા પીબી) ડેટાનો સંગ્રહ કરો
* ખૂબ જ ડેટા સઘન વર્કલોડ
* IOPS માટે ખૂબ જ ઉચ્ચ થ્રુપુટ

NoSQL માટે સારી રીતે અનુકૂળ નમૂના ડેટા:

* ક્લિકસ્ટ્રીમ અને લોગ ડેટાનું ઝડપી ઇન્જેસ્ટ
* લીડરબોર્ડ અથવા સ્કોરિંગ ડેટા
* કામચલાઉ ડેટા, જેમ કે શોપિંગ કાર્ટ
* વારંવાર ઍક્સેસ કરાયેલ ('હોટ') કોષ્ટકો
* મેટાડેટા/લુકઅપ કોષ્ટકો

કેશીંગ પૃષ્ઠ લોડ સમયને સુધારે છે અને તમારા સર્વર અને ડેટાબેસેસ પરના ભારને ઘટાડી શકે છે.  આ મોડેલમાં, ડિસ્પેચર પહેલા જો વિનંતી કરવામાં આવી હોય તો તે શોધશે અને વાસ્તવિક અમલને બચાવવા માટે પાછલા પરિણામને પરત કરવાનો પ્રયાસ કરશે.

ડેટાબેઝને તેના પાર્ટીશનોમાં વાંચવા અને લખવાના સમાન વિતરણથી વારંવાર ફાયદો થાય છે.  લોકપ્રિય વસ્તુઓ વિતરણને ત્રાંસી કરી શકે છે, જેના કારણે અડચણો ઊભી થાય છે.  ડેટાબેઝની સામે કેશ મૂકવાથી ટ્રાફિકમાં અસમાન લોડ અને સ્પાઇક્સને શોષવામાં મદદ મળી શકે છે.

[રિવર્સ પ્રોક્સી](#reverse-proxy-web-server) અને કૅશ જેમ કે [વાર્નિશ](https://www.varnish-cache.org/) સ્થિર અને ગતિશીલ સામગ્રીને સીધી સેવા આપી શકે છે.  વેબ સર્વર્સ એપ્લીકેશન સર્વર્સનો સંપર્ક કર્યા વિના પ્રતિસાદો પરત કરીને વિનંતીઓને કેશ કરી શકે છે.

### ડેટાબેઝ કેશીંગ

તમારા ડેટાબેઝમાં સામાન્ય રીતે ડિફોલ્ટ રૂપરેખાંકનમાં કેશીંગના અમુક સ્તરનો સમાવેશ થાય છે, જે સામાન્ય ઉપયોગના કેસ માટે ઑપ્ટિમાઇઝ કરવામાં આવે છે.  ચોક્કસ વપરાશ પેટર્ન માટે આ સેટિંગ્સને ટ્વિક કરવાથી કાર્યક્ષમતામાં વધુ વધારો થઈ શકે છે.

### એપ્લિકેશન કેશીંગ

ઇન-મેમરી કેશ જેમ કે Memcached અને Redis એ તમારી એપ્લિકેશન અને તમારા ડેટા સ્ટોરેજ વચ્ચેના કી-વેલ્યુ સ્ટોર્સ છે.  ડેટા RAM માં રાખવામાં આવતો હોવાથી, તે સામાન્ય ડેટાબેસેસ કરતાં વધુ ઝડપી છે જ્યાં ડેટા ડિસ્ક પર સંગ્રહિત થાય છે.  ડિસ્ક કરતાં રેમ વધુ મર્યાદિત છે, તેથી [કેશ અમાન્યતા](https://en.wikipedia.org/wiki/Cache_algorithms) અલ્ગોરિધમ્સ જેમ કે [ઓછામાં ઓછા તાજેતરમાં વપરાયેલ (LRU)](https://en.wikipedia.org/wiki/Cache_replacement_policies#Least_recently_used)'col' અને 'કોલ'માં મદદ કરી શકે છે. RAM માં 'ગરમ' ડેટા.

રેડિસમાં નીચેની વધારાની સુવિધાઓ છે:

* દ્રઢતા વિકલ્પ
* બિલ્ટ-ઇન ડેટા સ્ટ્રક્ચર્સ જેમ કે સૉર્ટ કરેલા સેટ અને લિસ્ટ

તમે કેશ કરી શકો તેવા બહુવિધ સ્તરો છે જે બે સામાન્ય શ્રેણીઓમાં આવે છે: **ડેટાબેઝ ક્વેરીઝ** અને **ઑબ્જેક્ટ્સ**:

* પંક્તિ સ્તર
* ક્વેરી-સ્તર
* સંપૂર્ણ રીતે રચાયેલ શ્રેણીબદ્ધ વસ્તુઓ
* સંપૂર્ણ રેન્ડર કરેલ HTML

સામાન્ય રીતે, તમારે ફાઇલ-આધારિત કેશીંગને ટાળવાનો પ્રયાસ કરવો જોઈએ, કારણ કે તે ક્લોનિંગ અને ઓટો-સ્કેલિંગને વધુ મુશ્કેલ બનાવે છે.

### ડેટાબેઝ ક્વેરી સ્તર પર કેશીંગ

જ્યારે પણ તમે ડેટાબેઝની ક્વેરી કરો છો, ત્યારે ક્વેરીને કી તરીકે હેશ કરો અને પરિણામને કેશમાં સ્ટોર કરો.  આ અભિગમ સમાપ્તિ સમસ્યાઓથી પીડાય છે:

* જટિલ પ્રશ્નો સાથે કેશ્ડ પરિણામ કાઢી નાખવું મુશ્કેલ છે
* જો ટેબલ સેલ જેવા ડેટાનો એક ભાગ બદલાય છે, તો તમારે બદલાયેલ કોષને સમાવી શકે તેવી બધી કેશ્ડ ક્વેરીઝ કાઢી નાખવાની જરૂર છે.

### ઑબ્જેક્ટ સ્તર પર કેશીંગ

તમારા ડેટાને ઑબ્જેક્ટ તરીકે જુઓ, જે તમે તમારા એપ્લિકેશન કોડ સાથે કરો છો તેના જેવું જ.  તમારી એપ્લિકેશનને ડેટાબેઝમાંથી ડેટાસેટને ક્લાસ ઇન્સ્ટન્સ અથવા ડેટા સ્ટ્રક્ચરમાં એસેમ્બલ કરવા દો:

* ઑબ્જેક્ટને કૅશમાંથી દૂર કરો જો તેનો અંતર્ગત ડેટા બદલાઈ ગયો હોય
* અસુમેળ પ્રક્રિયા માટે પરવાનગી આપે છે: કામદારો નવીનતમ કેશ્ડ ઑબ્જેક્ટનો ઉપયોગ કરીને ઑબ્જેક્ટ્સને ભેગા કરે છે

શું કેશ કરવું તેના સૂચનો:

* વપરાશકર્તા સત્રો
* સંપૂર્ણપણે રેન્ડર કરેલ વેબ પૃષ્ઠો
* પ્રવૃત્તિ સ્ટ્રીમ્સ
* વપરાશકર્તા ગ્રાફ ડેટા

### કેશ ક્યારે અપડેટ કરવી

તમે કૅશમાં માત્ર મર્યાદિત માત્રામાં ડેટા સ્ટોર કરી શકો છો, તેથી તમારે તમારા ઉપયોગના કેસ માટે કઈ કૅશ અપડેટ વ્યૂહરચના શ્રેષ્ઠ કામ કરે છે તે નિર્ધારિત કરવાની જરૂર પડશે.

#### કેશ-બાજુ

એપ્લિકેશન સ્ટોરેજમાંથી વાંચવા અને લખવા માટે જવાબદાર છે.  કેશ સ્ટોરેજ સાથે સીધો સંપર્ક કરતું નથી.  એપ્લિકેશન નીચે મુજબ કરે છે:

* કેશમાં પ્રવેશ માટે જુઓ, પરિણામે કેશ ચૂકી જાય છે
* ડેટાબેઝમાંથી એન્ટ્રી લોડ કરો
* કેશમાં એન્ટ્રી ઉમેરો
* રીટર્ન એન્ટ્રી

```python
def get_user(self, user_id):
    user = cache.get("user.{0}", user_id)
    if user is None:
        user = db.query("SELECT * FROM users WHERE user_id = {0}", user_id)
        if user is not None:
            key = "user.{0}".format(user_id)
            cache.set(key, json.dumps(user))
    return user
```

[Memcached](https://memcached.org/) નો ઉપયોગ સામાન્ય રીતે આ રીતે થાય છે.

કેશમાં ઉમેરાયેલ ડેટાના અનુગામી વાંચન ઝડપી છે.  કેશ-એસાઇડને બેકાર લોડિંગ તરીકે પણ ઓળખવામાં આવે છે.  માત્ર વિનંતી કરેલ ડેટા જ કેશ કરવામાં આવે છે, જે કેશને વિનંતી કરેલ ન હોય તેવા ડેટા સાથે ભરવાનું ટાળે છે.

##### ગેરલાભ(ઓ): cache-side

* દરેક કેશ મિસ ત્રણ ટ્રિપ્સમાં પરિણમે છે, જે નોંધપાત્ર વિલંબનું કારણ બની શકે છે.
* ડેટા જો ડેટાબેઝમાં અપડેટ કરવામાં આવે તો તે વાસી બની શકે છે.  આ સમસ્યાને ટાઈમ-ટુ-લાઈવ (TTL) સેટ કરીને ઘટાડવામાં આવે છે જે કેશ એન્ટ્રીના અપડેટને દબાણ કરે છે, અથવા રાઈટ-થ્રુનો ઉપયોગ કરીને.
* જ્યારે નોડ નિષ્ફળ જાય છે, ત્યારે તેને નવા, ખાલી નોડ દ્વારા બદલવામાં આવે છે, જે લેટન્સીમાં વધારો કરે છે.

એપ્લિકેશન મુખ્ય ડેટા સ્ટોર તરીકે કેશનો ઉપયોગ કરે છે, તેમાં ડેટા વાંચવા અને લખે છે, જ્યારે કેશ ડેટાબેઝને વાંચવા અને લખવા માટે જવાબદાર છે:

* એપ્લિકેશન કેશમાં એન્ટ્રી ઉમેરે/અપડેટ કરે છે
* કેશ સિંક્રનસ રીતે ડેટા સ્ટોરમાં એન્ટ્રી લખે છે
* પાછા ફરો

એપ્લિકેશન કોડ:

```python
set_user(12345, {"foo":"bar"})
```

કેશ કોડ:

```python
def set_user(user_id, values):
    user = db.query("UPDATE Users WHERE id = {0}", user_id, values)
    cache.set(user_id, user)
```

રાઇટ-થ્રુ રાઇટ ઑપરેશનને કારણે એકંદરે ધીમી કામગીરી છે, પરંતુ માત્ર લખેલા ડેટાના અનુગામી વાંચન ઝડપી છે.  ડેટા વાંચવા કરતાં ડેટા અપડેટ કરતી વખતે વપરાશકર્તાઓ સામાન્ય રીતે લેટન્સી પ્રત્યે વધુ સહનશીલ હોય છે.  કેશમાંનો ડેટા વાસી નથી.

##### ગેરલાભ(ઓ): લખો

* જ્યારે નિષ્ફળતા અથવા સ્કેલિંગને કારણે નવો નોડ બનાવવામાં આવે છે, ત્યારે ડેટાબેઝમાં એન્ટ્રી અપડેટ ન થાય ત્યાં સુધી નવો નોડ એન્ટ્રીઓને કેશ કરશે નહીં.  રાઇટ થ્રુ સાથે જોડાણમાં કેશ-બાજુ આ સમસ્યાને ઘટાડી શકે છે.
* લખાયેલ મોટા ભાગનો ડેટા ક્યારેય વાંચી શકાતો નથી, જેને TTL વડે ઘટાડી શકાય છે.

##### ગેરલાભ(ઓ): લખવા પાછળ

* જો કેશ ડેટા સ્ટોરને હિટ કરતા પહેલા તેની સામગ્રી નીચે જાય તો ડેટા નુકશાન થઈ શકે છે.
* કેશ-એસાઇડ અથવા રાઇટ-થ્રુને અમલમાં મૂકવા કરતાં લખવા-પાછળને અમલમાં મૂકવું વધુ જટિલ છે.

તમે કેશને તેની સમાપ્તિ પહેલા કોઈપણ તાજેતરમાં એક્સેસ કરેલ કેશ એન્ટ્રીને આપમેળે રિફ્રેશ કરવા માટે ગોઠવી શકો છો.

જો કેશ ભવિષ્યમાં કઇ આઇટમ્સની જરૂર પડવાની સંભાવના છે તેની ચોક્કસ આગાહી કરી શકે તો રિફ્રેશ-આગળના પરિણામે લેટન્સી વિ રીડ-થ્રુમાં ઘટાડો થઈ શકે છે.

##### ગેરલાભ(ઓ): રિફ્રેશ-આગળ

* ભવિષ્યમાં કઈ વસ્તુઓની જરૂર પડવાની શક્યતા છે તેની ચોક્કસ આગાહી ન કરવાથી તાજું-આગળ કર્યા વિના કામગીરીમાં ઘટાડો થઈ શકે છે.

### ગેરલાભ(ઓ): કેશ

* [cache invalidation](https://en.wikipedia.org/wiki/Cache_algorithms) દ્વારા ડેટાબેઝ જેવા કેશ અને સત્યના સ્ત્રોત વચ્ચે સુસંગતતા જાળવવાની જરૂર છે.
* કેશ અમાન્યતા એ એક મુશ્કેલ સમસ્યા છે, કેશ ક્યારે અપડેટ કરવી તેની સાથે સંકળાયેલ વધારાની જટિલતા છે.
* એપ્લિકેશનમાં ફેરફાર કરવાની જરૂર છે જેમ કે Redis અથવા memcached ઉમેરવા.

અસુમેળ વર્કફ્લો ખર્ચાળ કામગીરી માટે વિનંતીનો સમય ઘટાડવામાં મદદ કરે છે જે અન્યથા ઇન-લાઇન કરવામાં આવશે.  તેઓ સમય-વપરાશનું કામ અગાઉથી કરીને પણ મદદ કરી શકે છે, જેમ કે ડેટાનું સામયિક એકત્રીકરણ.

### સંદેશ કતાર

સંદેશ કતાર સંદેશાઓ પ્રાપ્ત કરે છે, પકડી રાખે છે અને વિતરિત કરે છે.  જો ઑપરેશન ઇનલાઇન કરવા માટે ખૂબ ધીમું હોય, તો તમે નીચેના વર્કફ્લો સાથે સંદેશ કતારનો ઉપયોગ કરી શકો છો:

* એપ્લિકેશન કતારમાં નોકરી પ્રકાશિત કરે છે, પછી વપરાશકર્તાને નોકરીની સ્થિતિ વિશે સૂચિત કરે છે
* એક કાર્યકર કતારમાંથી કામ ઉપાડે છે, તેની પ્રક્રિયા કરે છે, પછી કામ પૂર્ણ થવાનો સંકેત આપે છે

વપરાશકર્તા અવરોધિત નથી અને કાર્ય પૃષ્ઠભૂમિમાં પ્રક્રિયા કરવામાં આવે છે.  આ સમય દરમિયાન, ક્લાયન્ટ વૈકલ્પિક રીતે કાર્ય પૂર્ણ થયું હોય તેવું લાગે તે માટે થોડી માત્રામાં પ્રક્રિયા કરી શકે છે.  ઉદાહરણ તરીકે, જો કોઈ ટ્વીટ પોસ્ટ કરી રહ્યાં હોય, તો ટ્વીટ તમારી ટાઈમલાઈન પર તરત જ પોસ્ટ થઈ શકે છે, પરંતુ તમારી ટ્વિટ વાસ્તવમાં તમારા બધા અનુયાયીઓને પહોંચાડવામાં થોડો સમય લાગી શકે છે.

**[Redis](https://redis.io/)** સરળ મેસેજ બ્રોકર તરીકે ઉપયોગી છે પરંતુ સંદેશાઓ ગુમ થઈ શકે છે.

**[RabbitMQ](https://www.rabbitmq.com/)** લોકપ્રિય છે પરંતુ તમારે 'AMQP' પ્રોટોકોલને અનુકૂલિત કરવાની અને તમારા પોતાના નોડ્સનું સંચાલન કરવાની જરૂર છે.

**[Amazon SQS](https://aws.amazon.com/sqs/)** હોસ્ટ કરેલ છે પરંતુ તેમાં વધુ વિલંબતા હોઈ શકે છે અને સંદેશાઓ બે વાર વિતરિત થવાની સંભાવના છે.

### કાર્ય કતાર

કાર્ય કતાર કાર્યો અને તેમના સંબંધિત ડેટા પ્રાપ્ત કરે છે, તેમને ચલાવે છે, પછી તેમના પરિણામો પહોંચાડે છે.  તેઓ શેડ્યુલિંગને સમર્થન આપી શકે છે અને પૃષ્ઠભૂમિમાં કોમ્પ્યુટેશનલી-સઘન નોકરીઓ ચલાવવા માટે ઉપયોગમાં લઈ શકાય છે.

**[સેલેરી](https://docs.celeryproject.org/en/stable/)** શેડ્યૂલિંગ માટે સપોર્ટ ધરાવે છે અને મુખ્યત્વે પાયથોન સપોર્ટ ધરાવે છે.

### પીઠનું દબાણ

જો કતાર નોંધપાત્ર રીતે વધવા લાગે છે, તો કતારનું કદ મેમરી કરતાં મોટું થઈ શકે છે, પરિણામે કેશ ચૂકી જાય છે, ડિસ્ક રીડ થાય છે અને ધીમી કામગીરી પણ થાય છે.  [પાછળનું દબાણ](http://mechanical-sympathy.blogspot.com/2012/05/apply-back-pressure-when-overloaded.html) કતારના કદને મર્યાદિત કરીને મદદ કરી શકે છે, તેથી ઉચ્ચ થ્રુપુટ દર અને કતારમાં પહેલાથી જ નોકરીઓ માટે સારો પ્રતિસાદ સમય જાળવી શકે છે.  એકવાર કતાર ભરાઈ જાય, પછી ક્લાયંટને પછીથી ફરી પ્રયાસ કરવા માટે સર્વર વ્યસ્ત અથવા HTTP 503 સ્ટેટસ કોડ મળે છે.  ક્લાયન્ટ પછીના સમયે વિનંતીનો ફરી પ્રયાસ કરી શકે છે, કદાચ [ઘાતાંકીય બેકઓફ](https://en.wikipedia.org/wiki/Exponential_backoff) સાથે.

### હાઇપરટેક્સ્ટ ટ્રાન્સફર પ્રોટોકોલ (HTTP)

HTTP એ ક્લાયંટ અને સર્વર વચ્ચે ડેટાને એન્કોડિંગ અને પરિવહન કરવાની પદ્ધતિ છે.  તે એક વિનંતી/પ્રતિસાદ પ્રોટોકોલ છે: ક્લાયંટ વિનંતીઓ જારી કરે છે અને સર્વર્સ સંબંધિત સામગ્રી અને વિનંતી વિશે પૂર્ણતાની સ્થિતિની માહિતી સાથે પ્રતિસાદો આપે છે.  HTTP સ્વયં-સમાયેલ છે, જે વિનંતીઓ અને પ્રતિસાદોને ઘણા મધ્યવર્તી રાઉટર્સ અને સર્વર્સ દ્વારા વહેવા દે છે જે લોડ બેલેન્સિંગ, કેશીંગ, એન્ક્રિપ્શન અને કમ્પ્રેશન કરે છે.

મૂળભૂત HTTP વિનંતીમાં ક્રિયાપદ (પદ્ધતિ) અને સંસાધન (અંતિમ બિંદુ) નો સમાવેશ થાય છે.  નીચે સામાન્ય HTTP ક્રિયાપદો છે:

| ક્રિયાપદ | વર્ણન | આડેધડ* | સલામત | કેશેબલ |
|---|---|---|---|---|
| મેળવો | સંસાધન વાંચે છે | હા | હા | હા |
| પોસ્ટ | એક સંસાધન બનાવે છે અથવા પ્રક્રિયાને ટ્રિગર કરે છે જે ડેટાને હેન્ડલ કરે છે | ના | ના | હા જો પ્રતિભાવમાં તાજગીની માહિતી હોય તો |
| મૂકો | સંસાધન બનાવે છે અથવા બદલો | હા | ના | ના |
| પેચ | આંશિક રીતે સંસાધનને અપડેટ કરે છે | ના | ના | હા જો પ્રતિભાવમાં તાજગીની માહિતી હોય તો |
| કાઢી નાખો | સંસાધન કાઢી નાખે છે | હા | ના | ના |

*વિવિધ પરિણામો વિના ઘણી વખત કૉલ કરી શકાય છે.

HTTP એ એપ્લીકેશન લેયર પ્રોટોકોલ છે જે **TCP** અને **UDP** જેવા નીચલા-સ્તરના પ્રોટોકોલ પર આધાર રાખે છે.

### ટ્રાન્સમિશન કંટ્રોલ પ્રોટોકોલ (TCP)

<p align="center">
  <img src="images/JdAsdvG.jpg">
  <br/>
  <i><a href=http://www.wildbunny.co.uk/blog/2012/10/09/how-to-make-a-multi-player-game-part-1/>Source: How to make a multiplayer game</a></i>
</p>

TCP એ [IP નેટવર્ક](https://en.wikipedia.org/wiki/Internet_Protocol) પર કનેક્શન-લક્ષી પ્રોટોકોલ છે.  [હેન્ડશેક](https://en.wikipedia.org/wiki/Handshaking) નો ઉપયોગ કરીને કનેક્શન સ્થાપિત અને સમાપ્ત થાય છે.  મોકલવામાં આવેલ તમામ પેકેટો મૂળ ક્રમમાં અને ભ્રષ્ટાચાર વિના ગંતવ્ય સ્થાને પહોંચવાની ખાતરી આપે છે:

* દરેક પેકેટ માટે ક્રમ નંબરો અને [ચેકસમ ફીલ્ડ્સ](https://en.wikipedia.org/wiki/Transmission_Control_Protocol#Checksum_computation)
* [સ્વીકૃતિ](https://en.wikipedia.org/wiki/Acknowledgement_(data_networks)) પેકેટો અને સ્વચાલિત રીટ્રાન્સમિશન

જો મોકલનારને સાચો પ્રતિસાદ ન મળે, તો તે પેકેટોને ફરીથી મોકલશે.  જો ત્યાં બહુવિધ સમયસમાપ્તિ હોય, તો કનેક્શન છોડવામાં આવે છે.  TCP [ફ્લો કંટ્રોલ](https://en.wikipedia.org/wiki/Flow_control_(data)) અને [ભીડ નિયંત્રણ](https://en.wikipedia.org/wiki/Network_congestion#Congestion_control) પણ લાગુ કરે છે.  આ ગેરંટી વિલંબનું કારણ બને છે અને સામાન્ય રીતે UDP કરતા ઓછા કાર્યક્ષમ ટ્રાન્સમિશનમાં પરિણમે છે.

ઉચ્ચ થ્રુપુટ સુનિશ્ચિત કરવા માટે, વેબ સર્વર્સ મોટી સંખ્યામાં TCP કનેક્શન્સ ખુલ્લા રાખી શકે છે, જેના પરિણામે ઉચ્ચ મેમરી વપરાશ થાય છે.  વેબ સર્વર થ્રેડો અને કહો કે, [memcached](https://memcached.org/) સર્વર વચ્ચે મોટી સંખ્યામાં ખુલ્લા જોડાણો રાખવા તે ખર્ચાળ હોઈ શકે છે.  [કનેક્શન પૂલિંગ](https://en.wikipedia.org/wiki/Connection_pool) જ્યાં લાગુ હોય ત્યાં UDP પર સ્વિચ કરવા ઉપરાંત મદદ કરી શકે છે.

TCP એ એપ્લીકેશન માટે ઉપયોગી છે કે જેને ઉચ્ચ વિશ્વસનીયતાની જરૂર હોય પરંતુ ઓછા સમય માટે મહત્વપૂર્ણ હોય.  કેટલાક ઉદાહરણોમાં વેબ સર્વર, ડેટાબેઝ માહિતી, SMTP, FTP અને SSH નો સમાવેશ થાય છે.

UDP પર TCP નો ઉપયોગ કરો જ્યારે:

* તમારે અકબંધ આવવા માટે તમામ ડેટાની જરૂર છે
* તમે નેટવર્ક થ્રુપુટનો શ્રેષ્ઠ અંદાજ આપમેળે ઉપયોગ કરવા માંગો છો

### વપરાશકર્તા ડેટાગ્રામ પ્રોટોકોલ (UDP)

<p align="center">
  <img src="images/yzDrJtA.jpg">
  <br/>
  <i><a href=http://www.wildbunny.co.uk/blog/2012/10/09/how-to-make-a-multi-player-game-part-1/>Source: How to make a multiplayer game</a></i>
</p>

UDP જોડાણ રહિત છે.  ડેટાગ્રામ (પેકેટના સમાન)ની ખાતરી માત્ર ડેટાગ્રામ સ્તરે જ આપવામાં આવે છે.  ડેટાગ્રામ કદાચ તેમના ગંતવ્ય સુધી પહોંચી શકે છે અથવા બિલકુલ નહીં.  UDP ભીડ નિયંત્રણને સમર્થન આપતું નથી.  TCP સમર્થનની બાંયધરી વિના, UDP સામાન્ય રીતે વધુ કાર્યક્ષમ છે.

UDP પ્રસારણ કરી શકે છે, સબનેટ પરના તમામ ઉપકરણો પર ડેટાગ્રામ મોકલીને.  આ [DHCP](https://en.wikipedia.org/wiki/Dynamic_Host_Configuration_Protocol) સાથે ઉપયોગી છે કારણ કે ક્લાયન્ટને હજુ સુધી IP સરનામું મળ્યું નથી, આમ IP સરનામા વિના TCP ને સ્ટ્રીમ કરવાની રીતને અટકાવે છે.

UDP ઓછું ભરોસાપાત્ર છે પરંતુ તે VoIP, વિડિયો ચેટ, સ્ટ્રીમિંગ અને રીયલ ટાઇમ મલ્ટિપ્લેયર ગેમ્સ જેવા વાસ્તવિક સમયના ઉપયોગના કેસોમાં સારી રીતે કામ કરે છે.

TCP પર UDP નો ઉપયોગ કરો જ્યારે:

* તમારે સૌથી ઓછી વિલંબની જરૂર છે
* મોડો ડેટા ડેટા ગુમાવવા કરતાં વધુ ખરાબ છે
* તમે તમારી પોતાની ભૂલ સુધારણાનો અમલ કરવા માંગો છો

### દૂરસ્થ પ્રક્રિયા કૉલ (RPC)

<p align="center">
  <img src="images/iF4Mkb5.png">
  <br/>
  <i><a href=http://www.puncsky.com/blog/2016-02-13-crack-the-system-design-interview>Source: Crack the system design interview</a></i>
</p>

RPC માં, ક્લાયન્ટ અલગ સરનામાંની જગ્યા, સામાન્ય રીતે રિમોટ સર્વર પર એક્ઝિક્યુટ કરવાની પ્રક્રિયાનું કારણ બને છે.  ક્લાયંટ પ્રોગ્રામમાંથી સર્વર સાથે કેવી રીતે વાતચીત કરવી તેની વિગતોને અમૂર્ત કરીને, પ્રક્રિયાને કોડેડ કરવામાં આવે છે જાણે કે તે સ્થાનિક પ્રક્રિયા કૉલ હોય.  રિમોટ કૉલ્સ સામાન્ય રીતે સ્થાનિક કૉલ્સ કરતાં ધીમા અને ઓછા વિશ્વસનીય હોય છે તેથી તે સ્થાનિક કૉલ્સથી RPC કૉલ્સને અલગ પાડવા માટે મદદરૂપ છે.  લોકપ્રિય RPC ફ્રેમવર્કમાં [Protobuf](https://developers.google.com/protocol-buffers/), [Thrift](https://thrift.apache.org/), અને [Avro](https://avro.apache.org/docs/current/) નો સમાવેશ થાય છે.

RPC એ વિનંતી-પ્રતિસાદ પ્રોટોકોલ છે:

* **ક્લાયન્ટ પ્રોગ્રામ** - ક્લાયન્ટ સ્ટબ પ્રક્રિયાને કૉલ કરે છે.  પેરામીટર્સને સ્ટેક પર સ્થાનિક પ્રક્રિયા કોલની જેમ ધકેલવામાં આવે છે.
* **ક્લાયન્ટ સ્ટબ પ્રક્રિયા** - માર્શલ્સ (પેક) પ્રક્રિયા આઈડી અને વિનંતી સંદેશમાં દલીલો.
* **ક્લાયન્ટ કોમ્યુનિકેશન મોડ્યુલ** - OS ક્લાયંટ તરફથી સર્વર પર સંદેશ મોકલે છે.
* **સર્વર કમ્યુનિકેશન મોડ્યુલ** - OS આવનારા પેકેટોને સર્વર સ્ટબ પ્રક્રિયામાં પસાર કરે છે.
* **સર્વર સ્ટબ પ્રક્રિયા** - પરિણામોને અનમાર્શલ કરે છે, પ્રક્રિયા આઈડી સાથે મેળ ખાતી સર્વર પ્રક્રિયાને કૉલ કરે છે અને આપેલ દલીલો પસાર કરે છે.
* સર્વર પ્રતિસાદ ઉપરના પગલાંને વિપરીત ક્રમમાં પુનરાવર્તિત કરે છે.

નમૂના RPC કૉલ્સ:

```
GET /someoperation?data=anId

POST /anotheroperation
{
  "data":"anId";
  "anotherdata": "another value"
}
```

RPC વર્તણૂકોને ઉજાગર કરવા પર કેન્દ્રિત છે.  RPC નો ઉપયોગ ઘણીવાર આંતરિક સંદેશાવ્યવહાર સાથે કામગીરીના કારણોસર કરવામાં આવે છે, કારણ કે તમે તમારા ઉપયોગના કેસોને વધુ સારી રીતે ફિટ કરવા માટે હેન્ડ-ક્રાફ્ટ નેટિવ કૉલ્સ કરી શકો છો.

મૂળ લાઇબ્રેરી (ઉર્ફ SDK) પસંદ કરો જ્યારે:

* તમે તમારું લક્ષ્ય પ્લેટફોર્મ જાણો છો.
* તમે તમારા "તર્ક" ને કેવી રીતે એક્સેસ કરવામાં આવે છે તે નિયંત્રિત કરવા માંગો છો.
* તમે તમારી લાઇબ્રેરીમાંથી ભૂલ નિયંત્રણ કેવી રીતે થાય છે તે નિયંત્રિત કરવા માંગો છો.
* પ્રદર્શન અને અંતિમ વપરાશકર્તા અનુભવ એ તમારી પ્રાથમિક ચિંતા છે.

**REST** ને અનુસરતા HTTP API નો સાર્વજનિક API માટે વધુ વખત ઉપયોગ થાય છે.

#### ગેરલાભ(ઓ): RPC

* RPC ક્લાયંટ સેવા અમલીકરણ સાથે ચુસ્તપણે જોડાયેલા છે.
* દરેક નવા ઓપરેશન અથવા ઉપયોગના કેસ માટે એક નવું API વ્યાખ્યાયિત કરવું આવશ્યક છે.
* RPC ડીબગ કરવું મુશ્કેલ હોઈ શકે છે.
* તમે કદાચ અસ્તિત્વમાં રહેલી ટેક્નોલોજીનો લાભ ઉઠાવી શકશો નહીં.  ઉદાહરણ તરીકે, કેશીંગ સર્વર પર [RPC કૉલ્સ યોગ્ય રીતે કૅશ થાય છે](https://web.archive.org/web/20170608193645/http://etherealbits.com/2012/12/debunking-the-myths-of-rpc-rest/) તેની ખાતરી કરવા માટે વધારાના પ્રયત્નોની જરૂર પડી શકે છે. ### પ્રતિનિધિત્વ રાજ્ય ટ્રાન્સફર (REST)

REST એ ક્લાયંટ/સર્વર મોડેલને લાગુ કરતી આર્કિટેક્ચરલ શૈલી છે જ્યાં ક્લાયંટ સર્વર દ્વારા સંચાલિત સંસાધનોના સમૂહ પર કાર્ય કરે છે.  સર્વર સંસાધનો અને ક્રિયાઓનું પ્રતિનિધિત્વ પ્રદાન કરે છે જે કાં તો હેરફેર કરી શકે છે અથવા સંસાધનોનું નવું પ્રતિનિધિત્વ મેળવી શકે છે.  તમામ સંચાર સ્ટેટલેસ અને કેશેબલ હોવા જોઈએ.

રિસ્ટફુલ ઇન્ટરફેસના ચાર ગુણો છે:

* **સંસાધનોને ઓળખો (HTTP માં URI)** - કોઈપણ ઑપરેશનને ધ્યાનમાં લીધા વિના સમાન URI નો ઉપયોગ કરો.
* **પ્રસ્તુતિ સાથે બદલો (HTTP માં ક્રિયાપદો)** - ક્રિયાપદો, હેડરો અને મુખ્ય ભાગનો ઉપયોગ કરો.
* **સ્વ-વર્ણનાત્મક ભૂલ સંદેશ (HTTP માં સ્થિતિ પ્રતિભાવ)** - સ્ટેટસ કોડ્સનો ઉપયોગ કરો, વ્હીલને ફરીથી શોધશો નહીં.
* **[HATEOAS](http://restcookbook.com/Basics/hateoas/) (HTTP માટે HTML ઈન્ટરફેસ)** - તમારી વેબ સેવા બ્રાઉઝરમાં સંપૂર્ણપણે સુલભ હોવી જોઈએ.

નમૂના REST કૉલ્સ:

```
GET /someresources/anId

PUT /someresources/anId
{"anotherdata": "another value"}
```

REST ડેટા એક્સપોઝ કરવા પર કેન્દ્રિત છે.  તે ક્લાયંટ/સર્વર વચ્ચેના જોડાણને ઘટાડે છે અને ઘણીવાર સાર્વજનિક HTTP API માટે ઉપયોગમાં લેવાય છે.  REST એ URI, [હેડર દ્વારા પ્રતિનિધિત્વ](https://github.com/for-GET/know-your-http-well/blob/master/headers.md), અને GET, POST, PUT, DELETE અને PATCH જેવા ક્રિયાપદો દ્વારા સંસાધનોને ઉજાગર કરવાની વધુ સામાન્ય અને સમાન પદ્ધતિનો ઉપયોગ કરે છે.  સ્ટેટલેસ હોવાને કારણે, REST હોરીઝોન્ટલ સ્કેલિંગ અને પાર્ટીશન માટે ઉત્તમ છે.

#### ગેરલાભ(ઓ): REST

* ડેટાને એક્સપોઝ કરવા પર REST કેન્દ્રિત હોવાથી, જો સંસાધનો કુદરતી રીતે વ્યવસ્થિત ન હોય અથવા સરળ પદાનુક્રમમાં એક્સેસ કરવામાં ન આવે તો તે યોગ્ય ન હોઈ શકે.  ઉદાહરણ તરીકે, ઇવેન્ટના ચોક્કસ સેટ સાથે મેળ ખાતા પાછલા કલાકના તમામ અપડેટ કરેલા રેકોર્ડ પરત કરવા એ પાથ તરીકે સરળતાથી વ્યક્ત કરવામાં આવતા નથી.  REST સાથે, તે URI પાથ, ક્વેરી પેરામીટર્સ અને સંભવતઃ વિનંતીના મુખ્ય ભાગના સંયોજન સાથે અમલમાં મુકાય તેવી શક્યતા છે.
* REST સામાન્ય રીતે અમુક ક્રિયાપદો (GET, POST, PUT, DELETE અને PATCH) પર આધાર રાખે છે જે ક્યારેક તમારા ઉપયોગના કેસમાં બંધબેસતું નથી.  ઉદાહરણ તરીકે, સમયસીમા સમાપ્ત થયેલા દસ્તાવેજોને આર્કાઇવ ફોલ્ડરમાં ખસેડવા એ આ ક્રિયાપદોમાં સ્વચ્છ રીતે ફિટ ન પણ હોઈ શકે.
* નેસ્ટેડ વંશવેલો સાથે જટિલ સંસાધનો મેળવવા માટે ક્લાયંટ અને સર્વર વચ્ચે એક જ દૃશ્ય રેન્ડર કરવા માટે બહુવિધ રાઉન્ડ ટ્રિપ્સની જરૂર પડે છે, દા.ત. બ્લોગ એન્ટ્રીની સામગ્રી અને તે એન્ટ્રી પરની ટિપ્પણીઓનું આનયન. ચલ નેટવર્ક પરિસ્થિતિઓમાં કાર્યરત મોબાઇલ એપ્લિકેશનો માટે, આ બહુવિધ રાઉન્ડટ્રીપ્સ અત્યંત અનિચ્છનીય છે.
* સમય જતાં, API પ્રતિસાદમાં વધુ ફીલ્ડ્સ ઉમેરવામાં આવી શકે છે અને જૂના ક્લાયન્ટ્સ તમામ નવા ડેટા ફીલ્ડ્સ પ્રાપ્ત કરશે, તે પણ જેની તેમને જરૂર નથી, પરિણામે, તે પેલોડનું કદ ફૂલે છે અને મોટી વિલંબ તરફ દોરી જાય છે.

## સુરક્ષા

આ વિભાગ કેટલાક અપડેટ્સનો ઉપયોગ કરી શકે છે.  [કોન્ટ્રીબ્યુટીંગ](#કોન્ટ્રીબ્યુટીંગ)ને ધ્યાનમાં લો!

સુરક્ષા એ વ્યાપક વિષય છે.  જ્યાં સુધી તમારી પાસે નોંધપાત્ર અનુભવ, સુરક્ષા પૃષ્ઠભૂમિ ન હોય અથવા સુરક્ષાના જ્ઞાનની જરૂર હોય તેવા પદ માટે અરજી કરી રહ્યાં હોવ, તો તમારે કદાચ મૂળભૂત કરતાં વધુ જાણવાની જરૂર રહેશે નહીં:

* સંક્રમણમાં અને આરામમાં એન્ક્રિપ્ટ કરો.
* [XSS](https://en.wikipedia.org/wiki/Cross-site_scripting) અને [SQL ઇન્જેક્શન](https://en.wikipedia.org/wiki/SQL_injection) ને રોકવા માટે બધા વપરાશકર્તા ઇનપુટ્સ અથવા કોઈપણ ઇનપુટ પરિમાણોને સ્વચ્છ કરો.
* SQL ઇન્જેક્શનને રોકવા માટે પેરામીટરાઇઝ્ડ ક્વેરીઝનો ઉપયોગ કરો.
* [ઓછામાં ઓછા વિશેષાધિકાર] (https://en.wikipedia.org/wiki/Principle_of_least_privilege) ના સિદ્ધાંતનો ઉપયોગ કરો.
